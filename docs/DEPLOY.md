# Запуск и развёртывание

Здесь описано, как поднять сервис у себя и как мы держим его на командном сервере https://kosmo.hrumburum.space. Быстрее всего запуститься в Docker: он поднимает сервис в изолированных контейнерах, где уже собрано всё нужное, и хватает одной команды `make up` ([«Запустить у себя в Docker»](#запустить-у-себя-в-docker)). Для разработки удобнее запуск без Docker, на Python и uv ([«Запустить без Docker»](#запустить-без-docker)). На сервер код уезжает через `make deploy` ([«Развернуть на сервере»](#развернуть-на-сервере), [«Обновить сервер»](#обновить-сервер)).

Языковая модель для работы не нужна. Без неё сводка для экипажа собирается по шаблону, и это нормальный режим. Как мы подключаем к серверу модель и голос с компьютера команды, написано в разделе [«Модель и озвучка с ПК команды»](#модель-и-озвучка-с-пк-команды). Частые поломки собраны в таблице в конце ([«Если что-то сломалось»](#если-что-то-сломалось)).

## Запустить у себя в Docker

Compose (`docker compose`) поднимает несколько связанных контейнеров по одному файлу описания. У нас это `deploy/compose.yml`: база, API, воркер и Caddy, подробнее в [«Как устроен сервис»](#как-устроен-сервис). Понадобятся Docker 24+ с плагином compose v2 и свободные порты 80 и 443.

1. Создайте файл настроек из образца:

   ```sh
   cp .env.example .env
   ```

   Впишите в `.env` любой `POSTGRES_PASSWORD`, а `DOMAIN=localhost` оставьте как есть. Если в пароле есть `$`, его надо удвоить (`$$`), потому что compose подставляет переменные в `.env`.

2. Соберите образ и поднимите сервисы:

   ```sh
   make up
   ```

   Цель создаёт `data/raw`, `data/assessments` и `data/mirror` от вашего пользователя и выполняет `docker compose --env-file .env -f deploy/compose.yml up -d --build`.

3. Проверьте, что сервис отвечает через Caddy, веб-сервер на входе, который передаёт запросы в API:

   ```sh
   curl -s localhost/health
   ```

   Ответ такой: `{"status":"ok","raw_root":"/data/raw","worker_last_tick":"<время последнего тика воркера или null>"}`.

4. Откройте фронтенд `http://localhost/`. Старая страница живёт на `http://localhost/dev/`, описание API на `http://localhost/docs`.

5. Данные заранее готовить не нужно. Задание расчёта само докачивает открытые архивы на запрошенный период в `/data/mirror` и импортирует их в `/data/raw` (раздел [«Данные»](#данные)). Если у вас уже есть зеркало, собранное вне Docker командой `make fetch`, его можно импортировать сразу:

   ```sh
   docker compose --env-file .env -f deploy/compose.yml exec -T api python scripts/import_mirror.py --mirror /data/mirror
   ```

6. Остановить сервис:

   ```sh
   make down                                                      # данные и volume остаются
   docker compose --env-file .env -f deploy/compose.yml down -v   # удаляет ещё базу и сертификаты
   ```

Контейнеры пишут в `data/` от uid 1000. Если у вас на хосте другой uid, писать они не смогут, и поможет одна из команд:

```sh
sudo chown -R 1000:1000 data
chmod -R a+rwX data
```

Данные можно держать и в другом каталоге. Его задаёт `DATA_DIR`, абсолютным путём или путём относительно `deploy/`:

```sh
DATA_DIR=/srv/evarisk-data make up
```

### Образ без compose

Образ `evarisk` запускается и сам по себе. `docker run` поднимает API, а воркер запускается в том же контейнере через `docker exec`:

```sh
docker run -p 8000:8000 evarisk
docker exec <контейнер> python -m evarisk.worker
```

Базой в этом случае служит SQLite `/data/evarisk.db`. В образе заданы `EVARISK_DATABASE_URL=sqlite:////data/evarisk.db` и `EVARISK_MIRROR_ROOT=/data/mirror`, а каталог `/data` принадлежит пользователю `app` (D88). При запуске через compose вместо SQLite подставляется Postgres.

## Запустить без Docker

Нужны Python 3.12 (версия записана в `.python-version`), [uv](https://docs.astral.sh/uv/) для зависимостей Python и [Bun](https://bun.sh/) для сборки страницы. Сеть нужна на установку и воркеру: он опрашивает источники текущего режима и докачивает архивы на запрошенный период. Расчёт по уже загруженным данным и тесты работают без сети.

1. Подготовьте окружение и соберите страницу:

   ```sh
   cp .env.example .env
   make sync                          # зависимости Python в .venv по uv.lock
   make front                         # зависимости и сборка страницы в frontend/dist
   ```

   Если bun не в PATH, укажите его явно: `make front BUN=~/.bun/bin/bun`.

2. Запустите API и воркер:

   ```sh
   scripts/dev_server.sh start        # API и страница на http://localhost:8000/ (pid data/api.pid, лог data/api.log)
   scripts/dev_server.sh worker-start # воркер (pid data/worker.pid, лог data/worker.log)
   scripts/dev_server.sh status
   ```

3. Проверьте: страница открывается на `http://localhost:8000/`, описание API на `http://localhost:8000/docs`. Команда `curl localhost:8000/health` возвращает в том числе `worker_last_tick`, время последнего тика воркера.

4. После изменения кода перезапускайте оба процесса. Код они загружают только при старте.

   ```sh
   scripts/dev_server.sh restart
   ```

5. Остановить:

   ```sh
   scripts/dev_server.sh stop
   scripts/dev_server.sh worker-stop
   ```

Когда правите код, удобнее `make api` (uvicorn с автоперезагрузкой) и `make worker` в соседнем терминале. Для страницы есть `make front-dev`: dev-сервер Vite (`bun run dev`) на порту 4173, который проксирует API на :8000.

Воркер нужен для двух вещей. Страница ставит расчёт заданием (`POST /jobs`), а выполняет его воркер. И только воркер опрашивает семь источников текущего режима по их частоте: `nasa_oem`, `celestrak`, `swpc_live`, `donki`, `gfz_kp`, `socrates`, `meteor_docs`. Если воркер не запущен, задание висит в очереди, а строка статуса на странице пишет «воркер: не запускался». Работает без него только синхронный `POST /assessments`.

В `algorithm_version` результата попадает sha кода, который загрузил процесс. Если были незакоммиченные изменения, к нему добавляется `-dirty`. Настройки процессы читают из окружения и `.env`; все переменные перечислены в разделе [«Переменные окружения»](#переменные-окружения).

api раздаёт сборку `frontend/dist` с `/`, если такой каталог есть, а старую страницу `web/` с `/dev`. Нет сборки, и `web/` отдаётся с `/`. Каталог сборки меняется через `EVARISK_FRONTEND_DIST`. В Docker страницу собирает стадия `frontend` внутри образа.

Страницу можно посмотреть и совсем без API, на сохранённом ответе разбора 11 мая 2024. Запустите простой сервер и откройте `http://localhost:8001/?sample=1`:

```sh
uv run python -m http.server --directory web 8001
```

Переход к сырой записи в этом режиме не работает и показывает ошибку.

Чтобы показать запущенный у себя сервис кому-то снаружи, есть быстрый туннель Cloudflare. Туннель даёт временный публичный адрес `*.trycloudflare.com`, который ведёт на порт вашей машины. Нужен `cloudflared`.

```sh
scripts/dev_server.sh tunnel-start   # печатает адрес *.trycloudflare.com
scripts/dev_server.sh tunnel-stop
```

Адрес каждый раз новый. Входа в сервис нет, поэтому через туннель менять состояние источников нельзя: `POST /sources/{name}/state` и `POST /sources/{name}/refresh` отвечают 403 `tunnel_readonly`. Это поведение задаёт `EVARISK_TUNNEL_READONLY`, по умолчанию `true`.

## Развернуть на сервере

Наш сервер: `5.42.120.235`, домен `kosmo.hrumburum.space`. Сервис там работает в Docker под compose, а на входе стоит Caddy. Это веб-сервер, который слушает порты 80 и 443, сам получает сертификат Let's Encrypt и передаёт запросы в api. Сертификат он запрашивает при первом обращении к домену, а порт 80 нужен ему для проверки ACME и перенаправления на HTTPS.

От сервера нужно немного: Linux с Docker и плагином compose, пользователь в группе `docker` (или root) и открытые порты 22, 80 и 443. Для HTTPS домен должен смотреть на сервер записью A, а если у сервера есть IPv6, то и AAAA. Без домена сервис работает по HTTP на IP-адресе (см. [«Адрес сервера: домен и IP»](#адрес-сервера-домен-и-ip)).

### Шаги

1. Локально создайте `.env.prod` из `.env.example`. В нём нужны `DOMAIN` ([«Адрес сервера: домен и IP»](#адрес-сервера-домен-и-ip)), надёжный `POSTGRES_PASSWORD` и три строки для модели и голоса ([«Модель и озвучка с ПК команды»](#модель-и-озвучка-с-пк-команды)). Учётные данные Space-Track добавляйте, только если они правда нужны ([«Данные Space-Track»](#данные-space-track)).

   Файл лежит в `.gitignore`, коммитить его нельзя. Ключей языковой модели в нём нет: на сервер они не попадают, а без них сводка просто собирается по шаблону.

2. На новом сервере один раз поставьте прокси для DONKI, то есть посредника на хосте, через которого контейнеры ходят к DONKI ([«Сеть сервера»](#сеть-сервера)).

3. Запустите развёртывание со своей машины:

   ```sh
   make deploy HOST=root@5.42.120.235
   ```

   В общем виде это `make deploy HOST=user@host`. Если добавить `GIT_SHA=…` (`make deploy HOST=… GIT_SHA=…`), в `algorithm_version` попадёт это значение, а не версия, которую `make` вычисляет из локального HEAD.

4. Проверьте ответ (в общем виде `curl -s <адрес>/health`):

   ```sh
   curl -s https://kosmo.hrumburum.space/health
   ```

   Дальше по адресу сервера открываются фронтенд `<адрес>/`, описание API `<адрес>/docs`, документация `<адрес>/manual` и старая страница `<адрес>/dev/`. С доменом в первые секунды, пока нет сертификата, бывает 502 или ошибка TLS. Подождите полминуты и повторите.

### Что делает `make deploy`

1. Копирует проект в `~/evarisk` на сервере (`rsync -az --delete`). Не уезжают `.venv`, `.git`, кеши и архивы `*.zip`, файлы окружения `.env`, `.env.llm`, `.env.prod` (из них копируется только `.env.example`) и локальные исключения клона из `.git/info/exclude`. Не уезжают и `frontend/node_modules` с `frontend/dist`: фронтенд собирается в образе из исходников `frontend/`. Каталог `data/` не копируется целиком, так что сырые данные, расчёты, данные Space-Track, модели и логи остаются дома, а `data/` сервера `--delete` не трогает.
2. Отдельно дописывает открытое зеркало `data/mirror` к зеркалу сервера (`rsync -az` без `--delete`). Архивы, которые воркер докачал на сервере, при этом не пропадают. Из зеркала на сервере пересобирается `data/raw`.
3. Кладёт `.env.prod` на сервер как `~/evarisk/.env`, перезаписывая его при каждом запуске. Если `.env.prod` нет, `.env` на сервере придётся создать вручную.
4. Создаёт `data/raw`, `data/assessments`, `data/mirror`. При развёртывании от root отдаёт их uid 1000, пользователю `app` в образе, иначе контейнеры не смогли бы в них писать.
5. Выполняет `docker compose --env-file .env -f deploy/compose.yml -f deploy/compose.prod.yml up -d --build`. `compose.prod.yml` добавляет `restart: unless-stopped`, ограничение логов 3×10 МБ и прокси для DONKI. Профиль `voice` (синтез речи в контейнере) на сервере не поднимается.
6. Импортирует зеркало: `exec -T api python scripts/import_mirror.py --mirror /data/mirror`.

### Что открыто наружу

Снаружи виден только Caddy на 80 и 443. Порты `db` и `api` не публикуются, Postgres доступен только внутри сети compose.

Входа в сервис нет. Ручки заморозки и отключения источников (`POST /sources/{name}/state`) работают при прямом доступе; запрет действует только на запросы через туннель Cloudflare (`EVARISK_TUNNEL_READONLY`).

### Адрес сервера: домен и IP

`DOMAIN` подставляется в `deploy/Caddyfile` как адрес сайта, и от его вида зависит, что сделает Caddy:

| Значение `DOMAIN` | Что получается |
|---|---|
| `localhost` | локальный запуск, HTTP на порту 80 |
| `http://5.42.120.235` | только HTTP по IP, без сертификата и перенаправления |
| `kosmo.hrumburum.space, http://5.42.120.235` | домен получает HTTPS, ссылка по IP продолжает работать по HTTP |
| `kosmo.hrumburum.space` | только домен с HTTPS; по IP сервис больше не открывается |

Правило простое. Адрес со схемой `http://` Caddy обслуживает только по HTTP. Имя без схемы получает сертификат Let's Encrypt, и HTTP перенаправляется на HTTPS. Блок `http://localhost` для локального запуска остаётся при любом `DOMAIN`.

Сейчас на сервере стоит `DOMAIN=kosmo.hrumburum.space, http://5.42.120.235`. Пока DNS домена не был готов, мы жили на

```sh
DOMAIN=http://5.42.120.235
```

и сервис открывался на `http://5.42.120.235/`. На домен переходили так, и при переносе на другой сервер шаги те же:

1. В DNS заводим запись A `kosmo.hrumburum.space` на `5.42.120.235`. У сервера есть IPv6 (`2a03:6f00:a::b066`), поэтому запись AAAA либо не заводим, либо направляем на этот адрес. Let's Encrypt проверяет домен и по IPv6, и чужая AAAA сорвёт выдачу сертификата.
2. С любой машины проверяем, что имя ведёт только на адреса сервера:

   ```sh
   getent ahosts kosmo.hrumburum.space
   ```

3. В локальном `.env.prod` меняем строку `DOMAIN`:

   ```sh
   DOMAIN=kosmo.hrumburum.space, http://5.42.120.235
   ```

   Можно оставить только домен, `DOMAIN=kosmo.hrumburum.space`, но тогда ссылка по IP перестанет открывать сервис.

4. Разворачиваем. Compose пересоздаёт контейнер `caddy` с новым `DOMAIN`, данные и база остаются.

   ```sh
   make deploy HOST=root@5.42.120.235
   ```

5. Проверяем. Первая команда должна ответить 308 на `https://`, вторая вернуть `"status":"ok"`.

   ```sh
   curl -sI http://kosmo.hrumburum.space/
   curl -s https://kosmo.hrumburum.space/health
   ```

   Если что-то не так, смотрим журнал Caddy. Ошибки ACME почти всегда означают DNS или закрытый порт 80.

   ```sh
   ssh root@5.42.120.235 'cd ~/evarisk && docker compose --env-file .env -f deploy/compose.yml -f deploy/compose.prod.yml logs caddy --tail=50'
   ```

Откатиться можно тем же путём: вернуть `DOMAIN=http://5.42.120.235` и снова выполнить `make deploy`. Сертификаты лежат в volume `caddy_data` и переживают пересоздание контейнеров.

### Сеть сервера

С нашего сервера DONKI (`kauai.ccmc.gsfc.nasa.gov`) не отвечает по IPv4: соединение висит до таймаута. Проверяли 19 сентября 2026. `curl -4` за 15 с ответа не дождался, `curl -6` получил 200. Контейнеры Docker при этом ходят наружу только по IPv4, и источник `donki` падал с `ConnectError: [Errno 101] Network is unreachable`.

Сначала мы попробовали включить IPv6 в сети compose (`enable_ipv6`). На Docker 29 этого сервера это сломало встроенный DNS: контейнеры перестали находить `db` (SERVFAIL). Если такую пробу кто-то повторит, сеть compose придётся пересоздать. `down` без `-v` базу и данные не трогает.

```sh
cd ~/evarisk
docker compose --env-file .env -f deploy/compose.yml -f deploy/compose.prod.yml down
docker compose --env-file .env -f deploy/compose.yml -f deploy/compose.prod.yml up -d
```

В итоге контейнеры ходят наружу через прокси на хосте. Прокси здесь просто посредник: контейнер отдаёт ему соединение, а тот открывает его сам, уже с хоста, где IPv6 работает. Всё держится на трёх файлах:

- `deploy/egress_proxy.py` это HTTPS-прокси (метод CONNECT) на адресе моста `172.17.0.1:3128`. Пускает он только подсеть Docker 172.16.0.0/12. К цели прокси соединяется с хоста сначала по IPv6, а через 0.3 с параллельно и по IPv4. Запросы по HTTP без TLS он не проксирует.
- `deploy/evarisk-egress.service` запускает его как службу systemd `evarisk-egress` через `/usr/bin/python3`.
- `deploy/compose.prod.yml` задаёт api и worker `HTTPS_PROXY=http://172.17.0.1:3128` и `NO_PROXY` для имён compose, а httpx берёт прокси из окружения. Локальный `make up` этот файл не подключает, поэтому у себя прокси не нужен.

Ставится прокси один раз на сервер:

1. Создайте каталог:

   ```sh
   ssh root@<сервер> mkdir -p /opt/evarisk-egress
   ```

2. Скопируйте прокси и службу:

   ```sh
   scp deploy/egress_proxy.py root@<сервер>:/opt/evarisk-egress/
   scp deploy/evarisk-egress.service root@<сервер>:/etc/systemd/system/
   ```

3. На сервере включите службу и откройте контейнерам порт прокси:

   ```sh
   systemctl daemon-reload && systemctl enable --now evarisk-egress
   ufw allow from 172.16.0.0/12 to 172.17.0.1 port 3128 proto tcp
   ```

4. Проверьте `GET /sources`: у `donki` должно быть свежее `last_success_at` и пустое `last_error`.

## Обновить сервер

Обновление делается тем же `make deploy`, после него проверяем `/health`:

```sh
make deploy HOST=root@5.42.120.235
curl -s https://kosmo.hrumburum.space/health
```

Образ пересобирается, но слои зависимостей берутся из кеша. Для Python это так, пока не менялись `pyproject.toml` и `uv.lock`; для фронтенда, пока не менялись `frontend/package.json` и `frontend/bun.lock`. Сама сборка фронтенда повторяется при любом изменении в `frontend/`. Volume и `data/` остаются. Импорт зеркала идемпотентен, уже загруженные записи он пропускает.

Версия на сервере (`algorithm_version` в результате) это sha локального HEAD. Если в `src/` или `config/` рабочей копии есть незакоммиченные изменения, к нему добавляется `-dirty`: образ собирается из рабочей копии, а не из коммита.

Тем же `make deploy` на сервер доезжают новые адреса туннелей ([«Модель и озвучка с ПК команды»](#модель-и-озвучка-с-пк-команды)), смена `DOMAIN` ([«Адрес сервера: домен и IP»](#адрес-сервера-домен-и-ip)) и новые архивы в зеркале ([«Обновить зеркало»](#обновить-зеркало)).

## Модель и озвучка с ПК команды

Ключей модели на сервере нет, так мы решили в D91. Модель и синтез речи работают на компьютере команды, а сервер ходит к ним через быстрые туннели Cloudflare. К модели он обращается не напрямую, а через ретранслятор (relay). Это маленький сервис на том же компьютере: он принимает запрос с токеном, вызывает модель с локальными ключами и отдаёт обратно только текст.

```text
сервер (api) → туннель *.trycloudflare.com → ПК: ретранслятор 127.0.0.1:8020 → модель Qwen (ключи в .env.llm)
сервер (api) → туннель *.trycloudflare.com → ПК: служба синтеза tts/ 127.0.0.1:8010
```

### Включить

На компьютере команды:

1. Проверьте, что ключи модели лежат в `.env.llm`, а токен `EVARISK_LLM_RELAY_TOKEN` в `.env.relay`. В git оба файла не попадают.

2. Запустите ретранслятор:

   ```sh
   uv run uvicorn evarisk.briefing.relay:app --host 127.0.0.1 --port 8020
   ```

   Он вызывает модель с ключами из `.env.llm` и отвечает на `POST /complete`, только если пришёл заголовок `Authorization: Bearer <токен>`. Без токена будет 401, при отказе модели 503.

3. Запустите службу синтеза `tts/` на 127.0.0.1:8010. Это делает `scripts/dev_server.sh tts-start`, ему нужно окружение `tts/.venv` (см. `tts/README.md`). Проверка:

   ```sh
   curl -s 127.0.0.1:8010/health
   ```

4. Поднимите два туннеля. Журналы пишутся в `data/`:

   ```sh
   setsid nohup cloudflared tunnel --no-autoupdate --protocol http2 --url http://127.0.0.1:8020 > data/tunnel-relay.log 2>&1 &
   setsid nohup cloudflared tunnel --no-autoupdate --protocol http2 --url http://127.0.0.1:8010 > data/tunnel-tts.log 2>&1 &
   ```

5. Возьмите адреса туннелей из журналов, это строки вида `https://….trycloudflare.com`:

   ```sh
   grep -o 'https://[a-z0-9-]*\.trycloudflare\.com' data/tunnel-relay.log | tail -1
   grep -o 'https://[a-z0-9-]*\.trycloudflare\.com' data/tunnel-tts.log | tail -1
   ```

Дальше на машине, откуда вы разворачиваете:

6. Впишите в `.env.prod` три строки: `EVARISK_LLM_RELAY_URL` (туннель к 8020), `EVARISK_LLM_RELAY_TOKEN` (тот же токен, что в `.env.relay`) и `EVARISK_TTS_URL` (туннель к 8010).

7. Разверните:

   ```sh
   make deploy HOST=… GIT_SHA=…
   ```

8. Проверьте на любом расчёте. Должно получиться `llm`, `true` и имя модели.

   ```sh
   curl -s https://kosmo.hrumburum.space/assessments/<id>/briefing | jq -r '.source, .validated, .model'
   ```

Сервер выбирает `RelayClient`, когда ключей Qwen у него нет, а `EVARISK_LLM_RELAY_URL` задан. Если ключи Qwen в окружении всё же есть, они важнее ретранслятора.

### Когда ПК выключен или адрес туннеля сменился

Пока компьютер выключен или туннель упал, сервер отвечает сводкой по шаблону, а озвучку берёт на себя браузер.

Хуже то, что адрес быстрого туннеля меняется при каждом перезапуске `cloudflared`. После перезапуска туннеля или компьютера:

1. поднимите ретранслятор, службу синтеза и оба туннеля (шаги 2–4 выше);
2. возьмите новые адреса из журналов (шаг 5);
3. поправьте в `.env.prod` две строки, `EVARISK_LLM_RELAY_URL` и `EVARISK_TTS_URL`;
4. снова выполните `make deploy`.

Служба синтеза за туннелем открыта без токена. Наружу она отдаёт только звук того текста, который ей прислали.

### Ключи модели напрямую, без ретранслятора

Так модель подключают там, где лежат ключи, например на компьютере команды. На командный сервер ключи мы не кладём (D91). К тому же `make deploy` при каждом запуске перезаписывает `~/evarisk/.env` файлом `.env.prod`.

1. Задайте `QWEN_BASE_URL`, `QWEN_KEY_ID`, `QWEN_SECRET` и при необходимости `QWEN_MODEL`, имя развёртывания модели Qwen 3.8 в API (по умолчанию берётся значение из `briefing/llm.py`). Без Docker ключи можно положить в `.env` или в отдельный `.env.llm`, он читается следом; файл должен лежать в рабочем каталоге. В Docker годится только `.env`: compose передаёт его строки в api и worker через `env_file`, а `.env.llm` в контейнер не попадает.

2. Процесс api читает переменные при старте, так что после правки его нужно перезапустить: `scripts/dev_server.sh restart` без Docker или `make up` в Docker.

3. Проверьте:

   ```sh
   curl -s localhost/assessments/<id>/briefing | jq -r '.source, .validated, .model'
   ```

   Должно быть `llm`, `true` и имя модели. `template` значит, что ключей нет, модель не ответила или её текст не прошёл проверку чисел. Что именно случилось, написано в `violations`. Сами ключи в ответы и журналы не попадают (`SecretStr`).

4. Для озвучки задайте `EVARISK_TTS_URL`, адрес службы синтеза (каталог `tts/`, там же её описание). Служба отвечает на `POST /synthesize` с `{"text", "language"}` телом `audio/wav`. Без переменной `audio_url` пуст, `voice_error` называет причину, и страница читает текст средствами браузера.

### Расход и повторы

Одна сводка стоит одного обращения к модели, максимум двух: второе нужно, если текст нарушил проверку. При временном сбое (сеть, таймаут, 429, 5xx) каждое обращение повторяется до `QWEN_RETRIES` раз, по умолчанию 5, с паузами 0.5, 1, 2, 4 и 4 с. Встроенные повторы SDK выключены, а ошибка ключа или запроса не повторяется вовсе. Когда попытки кончились, сводка отвечает шаблоном с причиной «модель не ответила за 6 попыток: …».

Отказ по токену (401, 403, «jwt token not found») пересоздаёт клиент с новым токеном (D74), процесс перезапускать не нужно. Ответ модели кешируется рядом с расчётом и заново не запрашивается, пока не передан `refresh=true`. Сводку с отказом модели кеш не держит, и при следующем открытии модель спросят снова.

## Переменные окружения

Настройки разложены по нескольким файлам, и главное не перепутать, какой из них куда уезжает:

| Файл | Где лежит | Что внутри | В git | На сервер |
|---|---|---|---|---|
| `.env.example` | репозиторий | образец всех настроек | да | копируется как есть |
| `.env` | корень проекта; на сервере `~/evarisk/.env` | настройки запуска | нет | на сервере создаётся из `.env.prod` |
| `.env.prod` | только ваша машина | настройки сервера | нет, никогда не коммитить | копируется как `~/evarisk/.env` при каждом `make deploy` |
| `.env.llm` | компьютер команды | ключи Qwen | нет | нет |
| `.env.relay` | компьютер команды | токен ретранслятора | нет | нет |

Сами переменные:

| Переменная | Зачем | Пример | Обязательна |

## Данные

Всё, что сервис скачал и насчитал, лежит в `data/`. Этот каталог не попадает ни в git (`.gitignore`), ни в образ (`.dockerignore`). В Docker он монтируется в контейнеры как `/data`.

| Каталог или файл | Что там |
|---|---|
| `data/mirror/` | зеркало открытых архивов с манифестом `manifest.jsonl` (url, путь, `fetched_at`, sha256, размер, статус, Last-Modified, ETag, тип содержимого; D33) |
| `data/raw/` | сырое хранилище: файлы и индекс, неизменяемые; восстанавливается из зеркала |
| `data/assessments/` | сохранённые результаты расчётов, по файлу JSON на запрос |
| `data/evarisk.db` | SQLite с таблицами `source_state` и `jobs` при запуске без Docker; в compose это Postgres |
| `data/spacetrack/` | история GP Space-Track, только для своей учётной записи; не копируется на сервер и не коммитится (пользовательское соглашение, D13) |
| `data/*.pid`, `data/*.log` | pid и журналы `scripts/dev_server.sh` и туннелей |

База Postgres в Docker хранится в volume `pgdata`, сертификаты Caddy в `caddy_data`.

Готовить данные под нужный период руками не надо (D59). Задание расчёта в режимах «разбор» и «прогноз из прошлого» сначала смотрит, есть ли в хранилище суточные файлы потока протонов. Нужны сутки от трёх суток до отсечения (или начала поиска) до конца поиска. Недостающие сутки воркер докачивает из тех же открытых архивов, что и ручное зеркало: NCEI SWPC, GOES-18 SGPS, эфемериды NASA с запасом 10 суток, DONKI, GFZ Kp. Файлы ложатся в `data/mirror` с манифестом и импортируются в `data/raw` тем же кодом.

Время доступности записей выводится так же, как у ручного зеркала. Поэтому отсечение в «прогнозе из прошлого» работает одинаково на заранее загруженных и на докачанных данных. Одно окно это 40–60 файлов и меньше минуты; на странице докачка видна шагом «архив периода». Отчёт о ней попадает в ограничения результата: период, число файлов и сутки, которых в архиве не оказалось. В сеть ходит только воркер, поэтому синхронный `POST /assessments` архив не докачивает и подсказывает `POST /jobs`.

У докачки есть границы. Поток протонов берётся из архива GOES-18, а он начинается с 2022 года. Для более ранних дат и для суток моложе двух дней архивного файла нет. Сервис пишет об этом в ограничениях и не выдаёт отсутствие данных за спокойную обстановку. Мы проверяли докачку на 9–13 ноября 2025 и 15 июля 2024. Выключается она через `EVARISK_ARCHIVE_BACKFILL=false`.

Зеркало можно собрать и заранее. Уже скачанные файлы повторно не качаются.

```sh
make fetch                                  # по умолчанию 1 марта – 2 июля 2024, около 120 МБ
make fetch START=2025-11-01 END=2025-11-13
```

На 2026-09-18 в зеркале за март–июль 2024 лежат 52 файла OEM NASA JSC. Ещё там 1071 файл восьми суточных продуктов SWPC из архива NCEI: 3-day forecast, discussion, geomag_forecast, daypre, dayind, SGAS, RSGA, geoalert. К ним добавляются 124 суточных файла GOES-18 SGPS L2, 18 недельных выгрузок DONKI, Kp GFZ, прогноз MEO 2024 и страница списка протонных событий NOAA.

Сырое хранилище собирается из зеркала одной командой. Она импортирует 1268 записей, а повторный запуск ничего не дублирует.

```sh
uv run python scripts/import_mirror.py --mirror data/mirror
```

Время доступности и версию каждой записи импорт выводит из самого продукта. Записи текущего режима добавляет воркер, а API перечитывает индекс без перезапуска.

### Пересборка data/raw

На сервер `data/raw` не копируется. Его восстанавливают из зеркала и живых источников:

1. Остановите воркер:

   ```sh
   docker compose --env-file .env -f deploy/compose.yml stop worker
   ```

2. Удалите старое хранилище на хосте. На сервере под root новый каталог потом отдайте контейнерам, они пишут от uid 1000: `chown 1000:1000 data/raw`.

   ```sh
   rm -rf data/raw && mkdir data/raw
   ```

3. Импортируйте зеркало:

   ```sh
   docker compose --env-file .env -f deploy/compose.yml exec -T api python scripts/import_mirror.py --mirror /data/mirror
   ```

4. Запустите воркер. Текущие данные он подтянет сам по cadence адаптеров.

   ```sh
   docker compose --env-file .env -f deploy/compose.yml start worker
   ```

### Обновить зеркало

Новые архивы в зеркало добавляются только вне Docker. Потом зеркало уезжает на сервер обычным развёртыванием:

```sh
uv run python scripts/mirror_archives.py
make deploy HOST=root@5.42.120.235
```

### Данные Space-Track

Пользовательское соглашение Space-Track запрещает распространять данные. Поэтому каталог `data/spacetrack` исключён из `rsync`, в образ из `data/` не попадает ничего (`.dockerignore`), а в репозиторий он не коммитится (`.gitignore`).

Учётные данные `SPACETRACK_USER` и `SPACETRACK_PASS` нужны только скрипту `scripts/fetch_spacetrack_gp_history.py`. Адаптеры текущего режима их не используют (D33), так что на сервере эти строки в `.env` можно не заполнять. Если история GP всё же понадобится на сервере, её выкачивают там же под своей учётной записью, а не копируют.

## Если что-то сломалось

### Журналы и состояние

Начинать стоит с журналов. Локально это `make logs`, на сервере:

```sh
cd ~/evarisk && docker compose --env-file .env -f deploy/compose.yml logs -f --tail=100
```

Для одного сервиса добавьте его имя: `... logs -f api`, `... logs -f worker`, `... logs -f caddy`.

Состояние healthcheck показывает `ps`. `db` проверяется через `pg_isready`, `api` через `GET /health` изнутри контейнера.

```sh
docker compose --env-file .env -f deploy/compose.yml ps
```

Воркер на каждом тике печатает итог по каждому адаптеру: `fetched N`, `skipped: not due` или `error: ...`. Ошибки источников не прячутся, они лежат в `last_error` таблицы `source_state` и видны в `GET /sources`. Сырую запись можно открыть через `GET /evidence/{raw_id}`, а расчёты лежат файлами в `data/assessments`.

### Частые поломки

| Симптом | Причина | Что сделать |
|---|---|---|
| DONKI с ошибкой: у `donki` в `GET /sources` `ConnectError: [Errno 101] Network is unreachable` | с сервера DONKI отвечает только по IPv6, контейнеры ходят по IPv4, а прокси на хосте не работает | проверить службу `evarisk-egress` (`systemctl status evarisk-egress`) и правило ufw; установка в разделе [«Сеть сервера»](#сеть-сервера) |
| Контейнеры не видят `db`, в журнале SERVFAIL | в сети compose включали `enable_ipv6`, встроенный DNS сломан | убрать `enable_ipv6` и пересоздать сеть: `down`, затем `up -d` ([«Сеть сервера»](#сеть-сервера)) |
| Сводка по шаблону (`source` равно `template`) | нет ни ключей, ни ретранслятора, модель не ответила или текст не прошёл проверку чисел | прочитать `violations`; для сервера проверить, что ПК команды включён, а ретранслятор и туннели работают |
| Адрес туннеля сменился: на сервере сводка по шаблону и озвучка в браузере | `cloudflared` перезапускали, и быстрый туннель получил новый адрес | взять адреса из `data/tunnel-relay.log` и `data/tunnel-tts.log`, поправить `.env.prod`, `make deploy` ([«Когда ПК выключен или адрес туннеля сменился»](#когда-пк-выключен-или-адрес-туннеля-сменился)) |
| `audio_url` пуст, есть `voice_error` | нет `EVARISK_TTS_URL` или служба синтеза недоступна | на ПК проверить `curl -s 127.0.0.1:8010/health` и туннель к 8010; пока службы нет, текст читает браузер |
| 502 или ошибка TLS сразу после развёртывания с доменом | Caddy ещё не получил сертификат | повторить через полминуты |
| Сертификат так и не выдан | DNS не ведёт на сервер, есть чужая запись AAAA или закрыт порт 80 | `getent ahosts kosmo.hrumburum.space` и журнал `caddy` ([«Адрес сервера: домен и IP»](#адрес-сервера-домен-и-ip)) |
| compose пишет «POSTGRES_PASSWORD не задан в .env» | нет `.env` или строки с паролем | `cp .env.example .env` и вписать `POSTGRES_PASSWORD` |
| Пароль Postgres с `$` не подходит | compose подставляет переменные в `.env` | удвоить `$` (`$$`) |
| `make deploy` пишет «нет ~/evarisk/.env» | нет ни локального `.env.prod`, ни `.env` на сервере | создать `.env.prod` или вручную `~/evarisk/.env` на сервере |
| Контейнеры не могут писать в `data/` | каталоги созданы от root или от другого uid | `sudo chown -R 1000:1000 data` или `chmod -R a+rwX data` |
| Задание висит в очереди, на странице «воркер: не запускался» | воркер не запущен | без Docker `scripts/dev_server.sh worker-start`; в Docker смотреть `ps` и журнал `worker` |
| Без Docker после правки кода поведение старое | процессы загружают код только при старте | `scripts/dev_server.sh restart` |
| `POST /assessments` отвечает подсказкой про `POST /jobs` | архив периода докачивает только воркер | ставить расчёт со страницы или через `POST /jobs` |
| 403 `tunnel_readonly` | через туннель Cloudflare менять состояние источников нельзя | делать это с самой машины сервиса |

## Как устроен сервис

В compose четыре контейнера (`deploy/compose.yml`):

| Контейнер | Что делает | Порты |
|---|---|---|
| `db` | Postgres 16: состояние источников и задания | наружу не открыт |
| `api` | uvicorn: API, сборка фронтенда (`frontend/`, Vue 3 + Vite) с `/`, старая страница `web/` с `/dev` | 8000 только внутри сети compose |
| `worker` | `python -m evarisk.worker`: опрос источников по cadence и задания расчёта | нет |
| `caddy` | вход: все пути проксирует на `api:8000` | 80 и 443 |

Есть ещё необязательный `tts` для синтеза речи. Он поднимается только с профилем `voice` (`make up-voice`).

`api` и `worker` собираются из одного образа (`Dockerfile`). Сначала стадии `frontend-deps` и `frontend` на `oven/bun:1` ставят зависимости по `frontend/package.json` и `frontend/bun.lock` (`bun install --frozen-lockfile`) и собирают `frontend/dist` (`bun run build`). Стадия `builder` на `python:3.12-slim` собирает `.venv` (`uv sync --frozen --no-dev`). В итоговый образ попадают `.venv`, `src`, `config`, `web`, `scripts`, документы для раздела «Документация» (`README.md`, `CONTRIBUTING.md`, `docs/*.md`) и сборка фронтенда в `/app/frontend/dist`. Процессы работают от пользователя `app` с uid 1000. Фронтенд собирается только внутри образа, так что bun и node не нужны ни на хосте, ни на сервере.

Данные живут вне образа. Каталог `data/` проекта монтируется в контейнеры как `/data` (`EVARISK_RAW_ROOT=/data/raw`, `EVARISK_ASSESSMENTS_ROOT=/data/assessments`, зеркало в `/data/mirror`).

В образе нет git и каталога `.git`, поэтому sha кода приходит аргументом сборки `GIT_SHA`. `make up` и `make deploy` вычисляют его локально: короткий HEAD и суффикс `-dirty` при незакоммиченных изменениях в `src/` и `config/`. Через `EVARISK_GIT_SHA` значение попадает в `algorithm_version` результатов. Если собрать образ без аргумента, версия будет `nogit+cfg<хеш конфигов>`.

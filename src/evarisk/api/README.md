# api

Назначение: HTTP-контракт для фронтендера и мини-фронта. Расчёт либо синхронный (`POST /assessments`), либо заданием в очереди `db.jobs`, которое выполняет воркер (`POST /jobs`). Схемы в `schemas.py`, оркестрация в `service.py`, маршруты в `app.py`.

## Интерфейс
- `POST /assessments` (200, синхронный вариант, так помечен в OpenAPI), `GET /assessments`, `GET /assessments/{id}`, `GET /assessments/{id}/export`, `GET /evidence/{raw_id}`, `GET /evidence/{raw_id}/download`, `GET /health`. OpenAPI: `/docs`.
- `service.load_assessment(id, settings)` и все ручки с `{assessment_id}`: идентификатор расчёта это `^[0-9a-f]{12}$` (`uuid4().hex[:12]`). Идентификатор другого вида это 404 `not_found`, а не чтение файла: рядом с расчётом лежат файлы сводки `<id>.briefing.<вопрос>.<язык>.json`, и имя такого файла расчётом не считается. Файл, который не разбирается как `AssessmentResult` (битый JSON, несовпадение схемы), тоже 404 `not_found`, не 500.
- `POST /jobs`: тело как у `POST /assessments`, ответ 202 `{"job_id", "status": "queued"}`; ошибки валидации 400 до постановки в очередь. `GET /jobs/{id}`: `id`, `kind`, `params`, `status` (`queued`, `running`, `done`, `failed`), `progress` (`{step, fraction, at}` или `null`), `error`, `assessment_id`, `created_at`, `started_at`, `finished_at`; 404 для неизвестного id. Результат готового задания читается `GET /assessments/{assessment_id}` и совпадает с синхронным ответом на тот же запрос с точностью до `id` и `created_at`.
- `GET /health`: `status`, `raw_root`, `worker_last_tick` (время `last_attempt_at` строки `_worker` в `source_state` или `null`, если воркер ни разу не прошёл).
- `GET /sources`: для каждого адаптера реестра `name`, `products`, `cadence_s`, `supports_archive`, `state`, `reason`, `changed_at`, `last_attempt_at`, `last_success_at`, `last_error` (из `source_state`, источник без записи это `active`), `last_record_fetched_at` (максимум `fetched_at` по `RawStore.records(name)` или `null`), `records`. `POST /sources/{name}/state` с телом `{"state": "active" | "frozen" | "disabled", "reason": "…"}` (причина обязательна) отвечает 200 той же строкой; `POST /sources/{name}/refresh` создаёт задание `refresh` с `params = {"source": name}` и отвечает 202 `{"job_id", "status": "queued"}`; воркер обновляет только `active`, для `frozen` и `disabled` задание завершается `failed` с текстом. Незарегистрированный источник 404, недопустимое состояние или пустая причина 400.
- Архивные источники без адаптера (записи из зеркала: `goes_sgps`, `swpc_archive`, `swpc_spe`) входят в `GET /sources` с `archive_only = true` и `cadence_s = null`; `POST /sources/{name}/state` принимает и их, `POST /sources/{name}/refresh` для них отвечает 409 `archive_only`. `run_assessment(..., disabled)` и `build_trajectory(..., disabled)` читают хранилище через `store.without(disabled)`, в `limitations` добавляется `LIMIT_DISABLED_SOURCES` (D51).
- `GET /trajectory?start=<ISO>&end=<ISO>&step_minutes=<1..10, по умолчанию 1>&mode=<current|review, по умолчанию current>` (для фронтенда): траектория по OEM тем же путём, что `run_assessment` (`oem_for` и `from_oem`, `AsOf(None)` для `review`, `AsOf(utc_now())` для `current`), но без линий и без запаса по краям (`pad=0`); сетка от `start` до `end` включительно с шагом `step_minutes`, каждая точка сетки попадает в `samples` (6 ч при шаге 1 это 361 точка), `level` у всех точек `unknown`. Ответ `schemas.TrajectoryResponse`: поля `TrajectorySummary` (`provider`, `epoch`, `is_reconstruction`, `provenance`, `age_at_query_hours`, `samples[{t, lat_deg, lon_deg, alt_km, sunlit, mlat_deg, in_saa, level}]`) плюс `limitations: list[str]` (ограничения траектории, строка «линии риска на траектории не рассчитаны…», для `review` строка о реконструкции). 400 при интервале вне 1 минуты–48 часов, наивных датах, шаге вне 1–10 и режиме `replay`; 409 `no_trajectory`, когда нет эфемериды, доступной на момент запроса и покрывающей интервал с запасом в час. `service.build_trajectory(query, store)`.
- `GET /orbit/latest` (для пропагации в браузере через satellite.js `json2satrec` и подписи источника): `schemas.OrbitLatest` `{"omm": <первый объект массива JSON CelesTrak из последней по доступности записи celestrak/gp, как есть> | null, "provenance": Provenance | null, "oem": {"creation_date", "start_time", "stop_time", "provenance"} | null}`; последняя запись это `AsOf(store, None).latest(...)`, `published_at` и `data_version` через `provenance_of` (у celestrak `published_at = fetched_at`, `derived`, `gp latest`). Запись celestrak, в которой нет массива объектов OMM, это 500 `bad_record`, не `null`. `service.latest_orbit(store)`.
- `GET /rules` (экран настроек, только чтение конфигов): `schemas.RulesSnapshot` `{"windows": WindowRules как dict, "sep": SepConfig как dict без sources, "sources": {"windows": null, "sep", "meteors", "conjunctions", "dose_proxy": dict[str, str]}}` из `load_window_rules`, `load_sep_config`, `load_meteor_config`, `load_conjunction_config`, `load_dose_proxy_config`; у правил окон источников нет (веса и шаг это наше правило, комментарий в `config/windows.toml`), поэтому `null`, а не пустой словарь. `service.rules_snapshot()`.
- Сводка для экипажа (D58, модуль `briefing`): `GET /assessments/{id}/briefing?question=summary&language=ru&voice=false&refresh=false` отдаёт `Briefing` (`text`, `speech_text`, `source` llm или template, `model`, `validated`, `violations`, `facts`, `generated_at`, `algorithm_version`, `audio_url`, `voice_error`); сводка кешируется в `<assessments_root>/<id>.briefing.<question>.<language>.json`, `refresh=true` собирает заново. Неизвестный вопрос это 400 `unknown_question`, неизвестный язык 400 `unknown_language`, неизвестный расчёт 404. `GET /assessments/{id}/briefing/audio?question=&language=` отдаёт `audio/wav`, записанный при `voice=true`, иначе 404. `GET /briefing/latest?voice=` это сводка `summary` последнего расчёта в режиме `current` для внешнего терминала (скафандр, бортовой планшет), 404 с объяснением, когда таких расчётов нет. Числа в тексте модели проверены по фактам расчёта; без модели или при нарушении отвечает шаблон.
- Ограничения публичного доступа (middleware `_guard`, до маршрутов): запрос с `Content-Length` больше `MAX_BODY_BYTES` (262144) это 413 `too_large` без чтения тела; при `Settings.tunnel_readonly` (`EVARISK_TUNNEL_READONLY`, по умолчанию `true`) запрос с заголовком `cf-connecting-ip` или `cf-ray` (их ставит Cloudflare) на `POST /sources/{name}/state` и `POST /sources/{name}/refresh` это 403 `tunnel_readonly`; остальные ручки через туннель работают как прежде, с машины сервиса состояние меняется. `tests/e2e/test_tunnel_guard.py`.
- `create_app(settings=None, *, engine=None, registry=None, llm=None, synthesizer=None) -> FastAPI`: `llm` это клиент языковой модели для сводки (в рабочем запуске `default_llm()` по `QWEN_*`, в тестах подменённый, `None` означает шаблонную сводку), `synthesizer` это служба синтеза речи (по умолчанию `make_synthesizer(settings.tts_url)`); движок по `settings.database_url` (или переданный), `init_schema` при старте, движок доступен как `app.state.engine`; `registry` подменяет `sources.registry.adapters()`; в тестах `database_url="sqlite:///:memory:"` (StaticPool) и `worker.jobs.run_pending` вызывается вручную с тем же движком.
- Статика (`_mount_static`, после всех маршрутов API, потому что `Mount("/")` перехватывает любой путь, объявленный после него): если каталог `Settings.frontend_dist` существует (`EVARISK_FRONTEND_DIST`, по умолчанию `frontend/dist`; в образе `/app/frontend/dist` из стадии `frontend` Dockerfile), сборка фронтенда монтируется на `/` (`html=True`), а старая страница `web/` на `/dev`; иначе `web/` на `/`, как раньше. Хеш-роутер фронтенда не требует истории путей на сервере. Старая страница ссылается на `/style.css`, `/app.js`, `/vendor/plotly.min.js` и `/sample_result.json` абсолютными путями, поэтому на `/dev` она открывается без стилей и скрипта, пока пути в `web/index.html` и `web/app.js` не станут относительными.
- `schemas.AssessmentRequest`: `mode` из `current`, `review`, `replay`; `cutoff` только для `replay`; `duration_hours` 1–8; период поиска до 24 ч; окно ВКД внутри периода. Даты tz-aware, наивные отвергаются валидатором. Необязательное `constraints: Constraints | None = None` (класс из `windows.compare`, реэкспорт): `min_sunlit_fraction` в `[0, 1]` или `null`, `start_in_daylight` (по умолчанию `false`); значение вне диапазона это 400 и для `POST /assessments`, и для `POST /jobs` (D43).
- D80: `cutoff` позже `eva_start` отвергается (`ValueError` схемы, ответ 400 «момент отсечения cutoff позже начала ВКД eva_start: …»); `run_assessment` передаёт `cutoff` в `windows.compare.score`, окна-кандидаты со стартом раньше отсечения исключаются с причиной «окно начинается раньше момента отсечения».
- `service.run_assessment(req, store, settings, on_progress=None) -> AssessmentResult`: момент данных `t` это `None` для `review`, `utc_now()` для `current`, `cutoff` для `replay`; линии считаются один раз на периоде поиска, окна-кандидаты и запрошенное окно оцениваются по пересечению; результат сохраняется в `Settings.assessments_root/<id>.json`. `NoTrajectoryData`, когда нет OEM, доступного на момент `t` и покрывающего период с запасом в час. `on_progress(step, fraction)` вызывается на шагах `trajectory 0.2`, `line:sep_protons 0.5`, `line:meteor_showers 0.7`, `line:conjunctions 0.75`, `line:dose_proxy 0.8`, `line:illumination 0.85`, `windows 0.9`, `saved 1.0` (`PROGRESS_STEPS`).
- Линии в `lines` и `data_availability` по порядку: `sep_protons`, `meteor_showers`, `conjunctions`, `dose_proxy`, `illumination`. В штрафе окон (`scoring_lines`) участвуют `sep_protons`, `meteor_showers` и `conjunctions` при `availability != unusable_for_replay`; `dose_proxy` информационная (D34); `illumination` считается всегда, в `per_line` не входит и применяется только через `req.constraints`, которые передаются в `windows.compare.score` для всех кандидатов и запрошенного окна; `rules` ответа это `rules_applied` рекомендации плюс `constraint_rules(req.constraints)` (строки «ограничение освещённости: …»), ограничение линии освещённости попадает в `limitations` вместе с остальными (D43).
- `TrajectorySummary.saa_passes` (и в `GET /trajectory`): проходы через ЮАА как элементы картины с `rule` (порог 24 000 нТл, IGRF, источник Heirtzler NTRS 20000085550 из `config/trajectory.toml`), `note` (минимум |B| и его момент, эфемерида), `threshold_nt`, `provenance` (запись OEM), чтобы штриховка на временной картине открывала ту же панель деталей, что интервалы линий; пустой список без сверенного порога. Старые сохранённые результаты поля не содержат (`default_factory=list`).
- `TrajectorySummary.samples` в `AssessmentResult`: каждая вторая точка минутной сетки траектории с `level` линии SEP в этой точке; вне интервалов линии `unknown`. В `GET /trajectory` децимации нет: шаг сетки `from_oem` равен `step_minutes`.
- Объяснение рекомендации (D76, D78) дополняет `with_notes(rec, requested, span, sep, compared, dropped)`: фраза `exposure_plain` «Опасные отрезки в запрошенном окне: высокий уровень протонов 04:30–04:48; критический уровень протонов 04:48–05:00. После 05:00 UTC 10 мая опасных отрезков до конца периода поиска нет.» и фраза `unscored_plain` о линиях без архива на момент данных, которые в сравнении окон не участвуют («Сближения в сравнении окон не участвуют: архива отчётов о сближениях за то время нет.», и при отсутствии подходящего окна тоже) идут перед выбором ближайшего окна и числом равноценных; при неизмеренном потоке протонов на большей части периода второй фразой идёт `PLAIN_UNMEASURED` («Поток протонов не измерен на 6 ч 54 мин из 12 ч периода поиска. …»). Технический `reason` получает те же заметки прежним текстом. Ноль опасных минут в окне, где поток протонов не измерен, `with_notes` оговаривает через `windows.explain.forecast_zero` (D84): «Опасных минут в окне нет, но это по прогнозу, измерений потока протонов нет.»; фраза о неизмеренном потоке по-прежнему стоит раньше неё. Отрезки собирает `exposure_spans` один раз для обоих текстов.
- Причина рекомендации дополняется `_exposure_note`: «минуты high и critical в запрошенном окне: 04:39–04:48 high, …; после 2024-05-11 07:52 UTC таких минут в периоде поиска нет» (по линиям штрафа, не больше шести отрезков). В `rules` ответа входит `RULE_SCORING_LINES`: какие линии участвуют в сравнении окон и что `dose_proxy` и `illumination` без ограничений окно не исключают (D34, D43).
- `service.outside_archive_note(store, span)`: если линия протонов `missing` в историческом режиме и период поиска вне суток, покрытых файлами `goes_sgps` (сутки данных это дата доступности минус день), в `limitations` добавляется `LIMIT_OUTSIDE_ARCHIVE` с диапазоном дат архива; рекомендации при этом нет, ответ 200 с `insufficient`, не ошибка сервера.
- `limitations` результата: ограничения линий плюс `LIMIT_CONJUNCTIONS_HISTORICAL` (сближения не в штрафе в исторических режимах), `LIMIT_DOSE_INFORMATIONAL`, `LIMIT_REVIEW` в режиме `review`, `LIMIT_CURRENT_PAST_WINDOW` в режиме `current`, если период поиска целиком раньше момента данных (расчёт по всем данным, как разбор; SOCRATES покрывает только текущую неделю).
- `version.algorithm_version()`: `PROCESS_GIT_SHA` плюс `cfg` и sha256 конфигов `config/sep_line.toml` и `config/windows.toml`. Sha фиксируется один раз при импорте модуля (`git_sha()`): он описывает код, загруженный процессом, а не текущий HEAD; незакоммиченные изменения в `src/` и `config/` дают суффикс `-dirty`; переменная `EVARISK_GIT_SHA` (образ Docker) имеет приоритет; без git и переменной `nogit`. Хеш конфигов считается при каждом вызове, потому что конфиги читаются на каждый расчёт (D46).

## Инварианты
- Ответ API и сохранённый JSON это один и тот же объект; выгрузка строится из него.
- Ошибки всегда `{"error": {"code", "message"}}`; отсутствие данных это 409 или `missing`, никогда «благоприятно».
- Времена в ответе ISO-8601 с `Z`.

## Как тестировать
- `uv run pytest tests/e2e -q` (`tests/e2e/test_frontend_api.py`: `/trajectory` 11 мая 2024 00:00–06:00 review даёт 361 точку при шаге 1 и 73 при шаге 5, 49 часов это 400, июнь вне OEM фикстуры 409; `/orbit/latest` без записи celestrak даёт `omm null` и `oem` с `CREATION_DATE 2024-05-10T18:51:53.202Z`, с фикстурой `tests/fixtures/celestrak/gp_25544.json` `NORAD_CAT_ID 25544`; `/rules` даёт `windows.step_minutes 15` и `sep.s1_pfu 10`); `make api` и открыть `http://localhost:8000/`; для заданий рядом `make worker` (иначе задание остаётся `queued`, а `worker_last_tick` в `/health` пуст).
- Монтирование статики в `tests/e2e/test_frontend_api.py`: с временной сборкой `/` отдаёт её `index.html` и `/assets/*`, `/dev/` отдаёт `web/index.html`, `/health`, `/rules`, `/orbit/latest` отвечают; без сборки `/` отдаёт `web/`, `/dev/` это 404.
- Тесты помечены `e2e`; `make check-fast` их пропускает, `make check` запускает. Воркер в тестах не запускается: `tests/e2e/test_jobs_api.py` вызывает `run_pending` вручную.
- Ограничения освещённости в `tests/e2e/test_api.py`: по эфемериде фикстуры 10 мая 2024 тень 13:56–14:02 и 15:29–15:34, поэтому `start_in_daylight` исключает запрошенное окно 14:00 и кандидата 15:30 с причиной «ограничение освещённости: старт в тени», рекомендация уходит на 13:00; `min_sunlit_fraction 0.99` исключает все окна (доля света шестичасовых окон около 0.93); `min_sunlit_fraction 1.01` это 400.
- Докачка архива (D59): API в сеть не ходит. Синхронный `POST /assessments` на непокрытый период отвечает 409 `no_trajectory` с подсказкой про `POST /jobs`; задание воркера докачивает архив и передаёт отчёт в `run_assessment(extra_limitations=...)`. Шаг прогресса `archive` (0.1) стоит первым в `PROGRESS_STEPS`.
- Страховка по геометрии (D61): `service.access_geometry(access, requested, rec) -> AccessGeometry | None`, поле `geometry` результата. Кандидаты на «самое устойчивое окно» это предпочтительное и равнозначные; рекомендация не меняется.
- `POST /assessments/{id}/briefing/ask` тело `{text, language}`: свой вопрос по расчёту, ответ `Briefing` с `asked`; пустой или длиннее 300 знаков текст это 400, неизвестный расчёт 404.

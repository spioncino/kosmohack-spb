# Дизайн системы: прогнозирование внешних рисков и планирование ВКД на МКС


Контекст: КосмоХакатон 2026, трек «Прогнозирование внешних рисков и планирование ВКД на МКС».

## 1. Цель и рамки

Сервис для аналитика наземной группы планирования ВКД. Аналитик задаёт режим, начало и
длительность выхода и допустимый период начала; сервис получает открытые данные, считает
положение МКС, оценивает внешние факторы на траектории, сравнивает окна одинаковой длительности
и выдаёт рекомендацию либо объясняет, почему оснований для выбора нет. Каждое число в ответе
прослеживается до сырой записи источника.

Условия работы над проектом: один день хакатона и небольшая команда. Поэтому система строится
так, чтобы правила соблюдались механически, проверками при каждом коммите, а не по памяти.

В рамках: два и более механизма воздействия (космическая погода обязательна), режимы «сейчас»,
«исторический разбор» и «replay» для 1 мая — 30 июня 2024, сравнение окон, объяснения,
выгрузка, устойчивость к сбоям источников. Вне рамок: телеметрия скафандра, дозиметрия человека,
допуск к реальной ВКД, регистрация пользователей, графический глобус.

## 2. Зафиксированные решения

| № | Решение | Причина |
|---|---|---|
| D1 | Один Python-пакет `evarisk`, два процесса: `api` и `worker` | Т6: долгие операции и отказ источника не трогают API |
| D2 | Postgres 16 для индекса, разобранных таблиц, заданий, результатов | Два процесса пишут одновременно; блокировка заданий строкой |
| D3 | Сырые ответы источников хранятся байт в байт в томе, неизменяемо | Т1, Т8: прослеживаемость до исходной записи, воспроизводимость |
| D4 | Без миграций: таблицы перестраиваются из сырого командой `make reindex` | Меньше отказов за один день; сырое и есть источник истины |
| D5 | Все чтения данных идут через «вид на момент T» (`AsOf`) | Т4: replay это тот же код с другим T, его нельзя обойти случайно |
| D6 | Запрос пользователя это задание в таблице `jobs` | Статус длительной операции, восстановление после падения |
| D7 | Первичный источник исторической орбиты: NASA JSC OEM (`nasa-public-data` S3), второй: Space-Track GP_HISTORY | OEM открыт, содержит CREATION_DATE и манёвры; проверено 2026-09-18 |
| D8 | Текущая орбита: CelesTrak GP (без регистрации), SGP4 через `sgp4` | Проверено 2026-09-18 |
| D9 | Линии риска подключаемые, единый протокол; вторая линия выбирается по разведке данных | Владелец решил выбирать по данным; ТЗ требует два разных механизма |
| D10 | Интерфейс: FastAPI JSON API как продукт, статичный мини-фронт без сборки | Фронтендер заменит страницу, контракт API останется |
| D11 | Развёртывание: свой VPS, `docker compose`, Caddy с TLS | Жюри нужен доступ до конца проверки |
| D12 | Зависимости через `uv`, Python 3.12 в контейнере и локально через `.python-version` | Совместимость колёс numpy/sgp4; локальная 3.14 не используется |
| D13 | Данные Space-Track не попадают в репозиторий | Пользовательское соглашение запрещает передачу |
| D14 | Все времена tz-aware UTC во всём коде и API | ТЗ: основной формат UTC; наивные даты запрещены линтом |

## 3. Архитектура

### 3.1 Процессы и контейнеры

- `db`: Postgres 16, том `pgdata`.
- `api`: uvicorn + FastAPI. Создаёт задания, отдаёт результаты и доказательства, управляет источниками.
- `worker`: тот же образ, команда `evarisk worker`. Цикл обновления источников по интервалам из
  конфигурации и исполнение заданий из `jobs` с `SELECT ... FOR UPDATE SKIP LOCKED`.
- `caddy`: реверс-прокси, TLS по домену, раздаёт `web/` статикой.
- Тома: `pgdata`, `rawdata` (сырое хранилище), `ephem` (эфемериды DE421 и кеш).

### 3.3 Поток данных одного задания

1. API валидирует запрос, создаёт запись в `jobs` со статусом `queued`, отдаёт `job_id`.
2. Воркер берёт задание, ставит `running`, пишет `progress` по шагам.
3. Траектория: провайдер выбирается режимом и отсечением (раздел 6).
4. Каждая линия риска получает окно, траекторию и `AsOf(T)` и возвращает `LineAssessment`.
5. Объединение: линии остаются раздельными, связанные сигналы группируются в цепочку события
   и учитываются один раз на механизм.
6. Окна-кандидаты одинаковой длительности внутри периода поиска, сравнение по явным правилам,
   рекомендация или `InsufficientGrounds`.
7. Результат сохраняется в `assessments` с `algorithm_version` и списком `raw_id` использованных
   записей. Выгрузка строится только из сохранённого результата.
8. Для replay: отдельный шаг сверки прогноза с данными, опубликованными после T; результат
   сверки хранится отдельным полем и никогда не участвует в расчёте.

## 4. Модель данных

### 4.1 Сырое хранилище

Файл: `rawdata/<source>/<product>/<fetched_at ISO>_<sha256[:12]>.<ext>`. Запись неизменяема.
Таблица `raw_records`: `id`, `source`, `product`, `url`, `fetched_at`, `published_at`,
`published_at_kind` (`exact` | `derived` | `unknown`), `data_version`, `sha256`, `path`, `bytes`, `content_type`,
`http_status`, `notes`. Поле `published_at` означает момент доступности данных потребителю, а не момент измерения; выведенное значение всегда берётся в позднюю сторону (раздел 19). Повторный ответ с тем же `sha256` для того же `url` не дублируется.

`published_at` берётся из самого продукта: `:Issued:` в текстах SWPC, `messageIssueTime` в DONKI,
`CREATION_DATE` в OEM и GP, время файла в архивах NCEI. Если поле недоступно, `published_at_kind`
равно `unknown`, и запись помечается непригодной для строгого replay.

### 4.2 Разобранные таблицы

Каждая строка ссылается на `raw_id` и несёт `published_at`, `valid_from`, `valid_to`,
`kind` (`observation` | `external_forecast` | `computed`). Таблицы первого этапа:
`orbit_elements` (GP), `orbit_ephemeris_files` (OEM), `swpc_forecast_issues` (3-day, discussion,
geomag), `donki_notifications`, `kp_values` (nowcast и definitive отдельными строками с
`variant`), `proton_flux`, `conjunctions`, `meteor_shower_calendar`.
Таблицы перестраиваются из сырого командой `make reindex`.

### 4.3 Вид на момент T

`AsOf(t: datetime | None)`: единственная точка чтения разобранных таблиц и сырого индекса.
Фильтр `published_at <= t` для всех запросов; `published_at_kind == 'unknown'` исключается при
конечном `t`. `t = None` означает исторический разбор без ограничения. Прямые запросы к таблицам
из `risk/`, `windows/`, `orbit/` запрещены линтом.

### 4.4 Задания и результаты

`jobs`: `id`, `kind`, `params` (JSON), `status` (`queued` | `running` | `done` | `failed`),
`progress` (шаг и доля), `error`, `created_at`, `started_at`, `finished_at`, `assessment_id`.
`assessments`: `id`, `request` (JSON), `mode`, `cutoff`, `result` (JSON по схеме API),
`algorithm_version`, `raw_ids` (массив), `created_at`.
`source_state`: `source`, `state` (`active` | `frozen` | `disabled`), `changed_at`, `reason`,
`last_success_at`, `last_error`.

## 5. Ядро типов (`types.py`)

- `Provenance`: `raw_id`, `source`, `product`, `published_at`, `published_at_kind`, `data_version`, `url`.
- `Kind`: `observation` | `external_forecast` | `computed`.
- `Availability`: `available` | `missing` | `stale` | `unusable_for_replay`; значение без
  `Availability` не существует, отсутствие данных никогда не выражается нулём или `NaN`.
- `Level`: `none` | `elevated` | `high` | `critical` плюс `unknown`, когда данных нет.
- `Interval`: `start`, `end`, `level`, `kind`, `provenance[]`, `rule`, `note`; при
  неизвестных границах `start_uncertainty` и `end_uncertainty` как длительности.
- `LineAssessment`: `line`, `mechanism`, `intervals[]`, `availability`, `confidence`
  (`low` | `medium` | `high` с текстом «от чего зависит»), `limitations[]`, `chain_ids[]`.
- `Trajectory`: массив точек `t`, `lat`, `lon`, `alt_km`, `sunlit`, `geomag_lat`, `in_saa`,
  плюс `provider`, `epoch`, `provenance`, `is_reconstruction`.
- `Window`: `start`, `end`, `duration`.
- `WindowScore`: `window`, `per_line[]` (пересечение в часах по уровням), `completeness`,
  `excluded_reason | None`.
- `Recommendation`: `preferred: Window | None`, `reason`, `equivalents[]`, `insufficient: bool`,
  `rules_applied[]`.

Даты только `datetime` с `tzinfo=UTC`. Единицы фиксированы в именах полей (`alt_km`, `flux_pfu`).

## 6. Орбита

- Провайдер `oem`: интерполяция по файлу NASA JSC OEM (J2000, 15 суток, содержит ребусты).
  Выбор файла: последний с `CREATION_DATE <= T`, покрывающий интервал. Для `T = None` берётся
  файл с самой поздней `CREATION_DATE`, покрывающий интервал, и результат помечается
  `is_reconstruction = true`.
- Провайдер `gp`: SGP4 по набору элементов. Правило выбора набора: все наборы с
  `CREATION_DATE <= T`, из них ближайшая `EPOCH` к целевому времени; при наличии манёвра между
  эпохой и целевым временем траектория помечается ограниченно достоверной. Порядок публикации
  не совпадает с порядком эпох, выбор по «последнему опубликованному» запрещён.
- Текущий режим: CelesTrak GP, обновление по расписанию; в интерфейсе видны источник, эпоха,
  давность.
- Геометрия: ECI в геодезические координаты, флаг `sunlit` (skyfield, DE421), геомагнитная
  широта по дипольному приближению IGRF-эпохи 2020, флаг `in_saa` по фиксированному полигону
  из литературы с указанием источника.
- Траектория участвует в расчёте не менее одной линии: геомагнитная широта задаёт жёсткость
  обрезания для протонов, `in_saa` и `sunlit` задают ограничения окна.

## 7. Линии риска

Протокол `RiskLine`: `name`, `mechanism`, `required_products[]`,
`assess(window: Window, trajectory: Trajectory, asof: AsOf) -> LineAssessment`.
Линия обязана вернуть `availability = missing`, если нет обязательных продуктов, и не имеет
права возвращать `Level.none` при отсутствии данных.

Линии первого этапа:
- `sep_protons`: поток протонов GOES ≥10 и ≥100 MeV, пороги S-шкалы, привязка к траектории
  через жёсткость обрезания по Störmer с поправкой на Kp: интервал опасности возникает там,
  где траектория проходит высокие геомагнитные широты во время повышенного потока.
- `geomagnetic`: Kp nowcast и прогноз SWPC 3-day, уровни G-шкалы; вклад в риск только через
  снижение жёсткости обрезания и как условие, не как самостоятельная опасность для человека.
- `illumination`: тень и свет по траектории; это ограничение, не опасность; правило задаётся
  параметром запроса (минимальная доля освещённого времени или старт на свету), по умолчанию
  только отображается.
- Вторая линия по результатам разведки: `conjunctions` (SOCRATES для «сейчас», собственный
  расчёт из GP для истории с честной пометкой «разбор») либо `meteors` (календарь потоков и
  прогноз NASA MEO, статистическая оценка). Критерий выбора: наличие датированных данных за
  май–июнь 2024 и содержательная связь с траекторией или условиями работ.

Объединение: сводка это вектор по линиям, а не одно число. Общий уровень равен максимуму по
линиям, но показывается вместе с вектором. Полнота данных сводки равна минимуму по критичным
продуктам. Сигналы с общим `chain_id` (вспышка, CME, SEP, буря одного события) не суммируются.

Прогноз на 6 часов: по геомагнитной линии из SWPC 3-day forecast и уведомлений DONKI, по
протонной из внешних предупреждений и продолжения текущего потока с явной пометкой
`external_forecast` либо `computed`.

## 8. Окна

- Кандидаты: сетка стартов внутри периода поиска с шагом 15 минут, длительность одна для всех.
- Исключение: окно с интервалом `critical` любой линии или с `availability = missing` по
  критичному продукту не рекомендуется, причина сохраняется в `excluded_reason`.
- Ранжирование: часы пересечения с интервалами `high` и `elevated` с весами, затем полнота
  данных, затем неопределённость границ. Окна равнозначны (`equivalents`), когда разница штрафа
  не больше допуска и разница часов `high` + `critical` не больше одного шага сетки (D48);
  запрошенное окно остаётся предпочтительным, если равнозначно лучшему (D45).
- Минуты доступа частиц известны по траектории и Kp заранее: при внешнем прогнозе протонного
  события не ниже порога или идущем по DONKI событии без измеренного спектра они получают `high`
  как условная экспозиция (D47), поэтому окна различаются ещё до первого измерения потока.
- Если все окна исключены или неразличимы, ответ `insufficient = true` с объяснением.
- Изменение длительности это новый сценарий рядом с прежним, а не улучшение прежнего.
- Правила описаны в `windows/README.md` и выдаются в ответе как `rules_applied`.

## 9. Replay

Запрос с режимом `replay` содержит `cutoff`. Всё, что читают линии и орбита, проходит через
`AsOf(cutoff)`. Продукты с неизвестным временем публикации исключаются и перечисляются в
`limitations`. После расчёта модуль `replay` берёт `AsOf(None)` и сравнивает предсказанные
интервалы с наблюдениями: ошибка времени начала, заблаговременность, пропуски, ложные
предупреждения. Сверка хранится в `result.verification` и не влияет на рекомендацию.

## 10. API

Все времена ISO-8601 с суффиксом `Z`. Ошибки в формате `{"error": {"code", "message"}}`.

| Метод и путь | Назначение |
|---|---|
| `GET /health` | состояние API, базы, воркера |
| `GET /sources` | реестр источников, свежесть, состояние, последняя ошибка |
| `POST /sources/{name}/state` | `active` / `frozen` / `disabled` с причиной |
| `POST /sources/{name}/refresh` | принудительное обновление |
| `POST /assessments` | создать задание: `mode`, `cutoff?`, `eva_start`, `duration_h` (1–8), `search_start`, `search_end` (до 24 ч), `constraints?` |
| `GET /jobs/{id}` | статус, прогресс, ошибка, `assessment_id` |
| `GET /assessments/{id}` | полный результат: окно и режим, сводка траектории, таймлайн по линиям, предупреждения с доказательствами, сравнение, рекомендация, источники, ограничения, сверка replay |
| `GET /assessments/{id}/export` | zip: `report.md`, `result.json`, `sources.json`, `timeline.csv` |
| `GET /evidence/{raw_id}` | метаданные сырой записи и её содержимое |
| `GET /assessments` | список сохранённых расчётов |

Схемы ответов совпадают с типами раздела 5. OpenAPI генерируется FastAPI и является контрактом
для фронтендера.

## 11. Мини-фронт

Одна страница `web/index.html` с `app.js` без сборки, Plotly в `web/vendor/`. Блоки: форма
запроса (режим, дата, старт, длительность, период поиска, отсечение для replay), статус задания
с прогрессом, таймлайн линий с окном поверх, список предупреждений с раскрытием доказательств
и ссылкой на `/evidence`, таблица сравнения окон, панель источников с кнопками заморозки и
обновления, кнопка выгрузки. Наблюдение, внешний прогноз и расчёт различаются подписью и цветом.

## 12. Выгрузка

Архив собирается из сохранённого `assessments.result`. `result.json` это тот же JSON, что отдаёт
API. `report.md` рендерится из него шаблоном. `sources.json` содержит `raw_ids` с URL, временем
получения и публикации, хешами. `algorithm_version` = git commit + sha256 конфигурации правил.

## 13. Ошибки и неполнота

- Отказ источника: `source_state.last_error`, данные остаются доступными с пометкой давности,
  линия возвращает `stale` или `missing`, интерфейс показывает это отдельно от «воздействия нет».
- Квота или ограничение доступа: та же ветка, без сообщения о благоприятной обстановке.
- Падение воркера посреди задания: задание с `running` старше порога возвращается в `queued`.
- Заморозка источника: адаптер не вызывается, данные остаются на момент заморозки.

  nowcast за май 2024, OEM от 2024-05-12, срез GP history 9–12 мая, протоны GOES за 10–11 мая,
  снимок SOCRATES, календарь метеорных потоков 2024.
- Сеть в тестах заблокирована фикстурой pytest.
- `unit/`: парсеры; ожидаемые значения взяты из самих документов.
- `physics/`: SGP4 по GP против OEM в пределах 5 км на совпадающем времени; доля `sunlit` на

  12:00–18:00 даёт рекомендацию с провенансом каждого интервала; выгрузка равна ответу API.
- Правило: ожидаемые значения приходят извне кода. Снимки собственного вывода запрещены.

## 15. Процесс разработки и автоматические проверки

Файлы: `CONTRIBUTING.md` в корне, `README.md` в каждом модуле, `docs/CRITERIA.md`,
`docs/STATUS.md`, `docs/DECISIONS.md`, `docs/TASKS.md`, `docs/SOURCES.md`, `docs/DEPLOY.md`.

`make check`: `ruff format --check`, `ruff check`, `mypy --strict src`, `pytest`,
`scripts/check_honesty.py`, `scripts/check_docs.py`. `make check-fast` без `pytest e2e`.

`check_honesty.py` запрещает в `src/evarisk/{risk,windows,orbit,replay}`: `fillna(`,
`nan_to_num(`, `except: pass` и `except Exception: pass`, `datetime.now()` и `utcnow()` без зоны,
`or 0` и `or 0.0` в выражениях со значениями, `default=0` для измерений, прямой импорт моделей
таблиц в обход `AsOf`. Во всём `src/` запрещает обращения к читателю в комментариях.

`check_docs.py` при коммите: если изменён `src/evarisk/<m>/`, в этом же коммите изменена строка
`<m>` в `docs/STATUS.md`; у каждого модуля есть `README.md`. Хук ставится `make hooks`.

Порядок изменения: прочитать `README.md` модуля, строку задачи и её критерии в
`docs/CRITERIA.md`; реализовать с тестом на реальной фикстуре; `make check` зелёный; обновить
`STATUS.md` и `README.md` модуля при смене интерфейса; сообщение коммита
`<модуль>: <что сделано> [критерии]`. Решения фиксируются в `DECISIONS.md` до начала работы над ними.

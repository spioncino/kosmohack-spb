# API и сводка для экипажа

## Коротко

Сервис считает внешние риски выхода в открытый космос (ВКД) с МКС. Ему дают запрошенное окно и период поиска. В
ответ он возвращает риски по минутам, рекомендацию окна и короткую сводку для экипажа. Почти всё делается четырьмя
вызовами:

- `POST /jobs`, затем `GET /jobs/{id}` до статуса `done`: запустить расчёт и дождаться его;
- `GET /assessments/{id}`: прочитать результат;
- `GET /assessments/{id}/briefing`: получить сводку для экипажа;
- `GET /assessments/{id}/export`: скачать всё одним zip-архивом.

Интерактивное описание API с примерами открывается на запущенном сервисе: `http://localhost/docs` в Docker,
`http://localhost:8000/docs` без Docker. Примеры ниже написаны для запуска без Docker; в Docker порт `:8000` не
нужен. Смысл полей ответа (уровни, `kind`, окна, сверка) подробно разобран в `docs/MODEL.md`. На что опираются
пороги и правила, объясняет `docs/SCIENTIFIC_BASIS.md`.

## Словарь

На странице, в сводке и в этом документе мы называем вещи одинаково.

- Окно: отрезок времени выхода длиной `duration_hours`. Кандидаты идут с шагом 15 минут, шаг это наше правило.
- Период поиска: отрезок от `search_start` до `search_end`, внутри которого целиком лежит любое окно.
- Период допустимого начала: моменты, когда окно может начаться. Это от `search_start` до `search_end` минус
  длительность.
- Опасные минуты: минуты уровня `high` и `critical`. По ним окна сравниваются в первую очередь. У линии протонов
  это минуты экспозиции: протоны достают трассу МКС (D63).
- Повышенный фон: уровень `elevated`. Обстановка хуже спокойной, но опасных минут нет.
- Фон: уровень `none`, опасности по линии нет.
- Нет данных: уровень `unknown`. Пропуск данных не равен нулевому риску.
- Линия риска: один вид опасности или условия работ со своими интервалами уровня (`lines`).
- «Сейчас» (`current`), «Разбор по архиву» (`review`), «Прогноз из прошлого» (`replay`): три режима расчёта,
  подробнее в разделе [Запрос расчёта](#запрос-расчёта).
- Момент отсечения (`cutoff`): время, после которого данные для «Прогноза из прошлого» не видны.
- Откуда взято число (провенанс, `provenance`): ссылка на сырую запись с источником, продуктом, временем
  публикации, версией и адресом.
- Задание (`job_id`): расчёт или обновление источника в фоновой очереди.

Три перечня встречаются почти в каждом ответе:

| поле | значения |
|---|---|
| `level` | `none` фон, `elevated` повышенный фон, `high` высокий, `critical` критический, `unknown` нет данных |
| `kind` | `observation` наблюдение, `external_forecast` внешний прогноз, `computed` наш расчёт |
| `availability` | `available` данные есть, `missing` нет данных, `stale` данные устарели, `unusable_for_replay` нет архива источника |

## Расчёт и задания

### Зачем расчёт идёт через задание

Считать можно двумя путями. Мы почти всегда идём через задание: `POST /jobs`, потом опрос `GET /jobs/{id}`. Так
работают страница и приёмочные проверки. Синхронный `POST /assessments` считает прямо в запросе и годится, когда
архив за период уже лежит в хранилище.

Всё дело в архиве. «Разбору по архиву» и «Прогнозу из прошлого» нужны данные за прошедшие дни. Если в хранилище
их нет, задание сначала скачивает их из открытых архивов (D59). Это сеть и иногда минуты ожидания, а держать
столько времени открытый HTTP-запрос ненадёжно. Поэтому в сеть ходит только фоновый обработчик заданий, воркер.
Синхронный запрос архив не докачивает: без данных он отвечает 409 и в тексте ошибки советует `POST /jobs`.
Заодно задание сообщает свой шаг в `progress`, и страница показывает прогресс.

Что именно докачивается. Нужны сутки начиная за три дня до начала поиска и до его конца (D59). В «Прогнозе из
прошлого» отсчёт начинается за 10 суток до отсечения, если так выходит раньше (D80). Сутки без суточных файлов потока
протонов воркер берёт из тех же архивов, что и ручное зеркало: NCEI SWPC, GOES-18 SGPS, NASA OEM с запасом 10
суток, DONKI, GFZ Kp. Недостающие годовые прогнозы NASA MEO тоже докачиваются.

Время доступности записей выводится так же, как у зеркала, так что отсечение работает одинаково. Если сеть
подвела, задание не падает: расчёт идёт по тому, что есть, а отчёт о докачке попадает в `limitations`. Сутки позже
«сегодня минус двое суток» не запрашиваются, их файла в архиве ещё нет. В режиме «Сейчас» докачки нет. Выключить
её можно настройкой `EVARISK_ARCHIVE_BACKFILL=false`.

### Как опрашивать задание

1. Отправить `POST /jobs` с телом запроса. Ответ 202: `{"job_id": "…", "status": "queued"}`.
2. Раз в 1–2 секунды спрашивать `GET /jobs/{job_id}`. Страница спрашивает каждые 1.5 секунды.
3. Ждать `status` `done` или `failed`. По дороге будут `queued` (в очереди) и `running` (считается).
4. При `done` взять `assessment_id` и прочитать `GET /assessments/{assessment_id}`.
5. При `failed` причина лежит в `error`: класс ошибки и её текст.

```sh
JOB=$(curl -s localhost:8000/jobs -H 'Content-Type: application/json' -d '{
  "mode": "review",
  "eva_start": "2024-05-11T04:00:00Z", "duration_hours": 6,
  "search_start": "2024-05-11T00:00:00Z", "search_end": "2024-05-12T00:00:00Z"
}' | jq -r .job_id)
until curl -s localhost:8000/jobs/$JOB | jq -e '.status == "done" or .status == "failed"' >/dev/null; do
  sleep 2
done
ID=$(curl -s localhost:8000/jobs/$JOB | jq -r .assessment_id)
curl -s localhost:8000/assessments/$ID | jq '.recommendation.explanation'
```

Ответ `GET /jobs/{id}`:

| поле | что значит |
|---|---|
| `id` | идентификатор задания |
| `kind` | `assessment` это расчёт, `refresh` это обновление источника |
| `params` | тело запроса, как его сохранила очередь |
| `status` | `queued`, `running`, `done` или `failed` |
| `progress` | `{"step", "fraction", "at"}`: шаг, доля от 0 до 1 и время отметки; до старта `null` |
| `error` | причина при `failed`, иначе `null` |
| `assessment_id` | идентификатор готового расчёта при `done` |
| `created_at`, `started_at`, `finished_at` | когда задание создано, начато и закончено |

Шаги расчёта в `progress.step` идут так: `claimed` (0), `archive` (докачка, от 0.02 до 0.1), `trajectory` (0.2),
`line:sep_protons` (0.5), `line:meteor_showers` (0.7), `line:conjunctions` (0.75), `line:dose_proxy` (0.8),
`line:illumination` (0.85), `windows` (0.9), `saved` (1.0). У задания `refresh` шаг `fetched N`, где N это число
полученных записей. Задание, которое вернулось в очередь, получает шаг `requeued` и пояснение в `note`.

Воркер берёт задание примерно через секунду, потому что опрашивает очередь и между тиками. Задания идут по одному.
Задание `running` старше 10 минут возвращается в очередь. Отказ одного задания не останавливает остальные. Каждый
тик отмечается в строке `_worker` таблицы `source_state` (`tests/e2e/test_jobs_api.py`,
`tests/e2e/test_sources_api.py`, `tests/worker/`).

`GET /assessments` отдаёт список сохранённых расчётов, новые первыми: `id`, `created_at`, `mode`, `eva_start`.
Файл, который не разбирается как расчёт, в список не попадает.

### Запрос расчёта

Тело одно и то же у `POST /jobs` и `POST /assessments`.

| поле | что значит |
|---|---|
| `mode` | режим: `current` «Сейчас», `review` «Разбор по архиву», `replay` «Прогноз из прошлого» |
| `cutoff` | момент отсечения; только для `replay`, там обязателен; не позже `eva_start` (D80) |
| `eva_start` | запрошенное начало выхода, UTC |
| `duration_hours` | длительность выхода, от 1 до 8 часов |
| `search_start`, `search_end` | период поиска; окна целиком лежат в `[search_start, search_end]` |
| `constraints` | необязательно: условия по освещённости (D43), `min_sunlit_fraction` от 0 до 1 и `start_in_daylight` |

Сервис проверяет запрос и при любом нарушении отвечает HTTP 400 с объяснением:

- период поиска задаёт период допустимого начала, от `search_start` до `search_end` минус длительность;
- этот отрезок занимает от 15 минут (не меньше двух окон) до 24 часов, и `eva_start` лежит в нём; обе границы
  взяты из постановки задачи;
- `cutoff` бывает только в `replay` и не позже `eva_start`, иначе прогноз видел бы уже наступившие события (D80).

`constraints` в штраф окна не входят. Они только исключают окна, которые им не отвечают, так решено в D43.

Режимы различаются тем, какие данные видит расчёт:

- «Сейчас» (`current`) видит всё, что доступно в момент расчёта. `asof` в ответе равен времени расчёта.
- «Разбор по архиву» (`review`) видит все опубликованные данные, в том числе вышедшие позже. Это реконструкция, а
  не прогноз, и `asof` равен `null`.
- «Прогноз из прошлого» (`replay`) видит только то, что было доступно к моменту отсечения. `asof` равен `cutoff`, а
  после расчёта сервис сверяет прогноз с фактом.

В «Прогнозе из прошлого» эфемерида берётся только доступная на момент отсечения. Время доступности это поздний из
`CREATION_DATE` и S3 Last-Modified (D57). Если ни одна такая эфемерида не покрывает период поиска, API отвечает 409,
и это честный ответ. Так будет, например, с отсечением 20 апреля 2024 для окна 11 мая. Задание в этом случае
заканчивается `failed` с той же причиной в `error`. Окна, которые начинаются раньше момента отсечения, исключаются
(D80).

### Примеры запросов

Тело запроса из `tests/e2e/test_api.py`: исторический разбор 10 мая 2024, выход 14:00 UTC на 6 часов, период
поиска 13:00–22:00.

```sh
curl -s localhost:8000/assessments -H 'Content-Type: application/json' -d '{
  "mode": "review",
  "eva_start": "2024-05-10T14:00:00Z",
  "duration_hours": 6,
  "search_start": "2024-05-10T13:00:00Z",
  "search_end": "2024-05-10T22:00:00Z"
}'
```

Дальше окно 11 мая 2024 04:00–10:00 UTC с периодом поиска на сутки, 00:00–24:00, как в `docs/examples/` и
`docs/experiments/`. Первый запрос это разбор по архиву. Второй это прогноз из прошлого с отсечением 10 мая
12:30 UTC, сразу после выпуска 3-day forecast 12:30.

```sh
curl -s localhost:8000/assessments -H 'Content-Type: application/json' -d '{
  "mode": "review",
  "eva_start": "2024-05-11T04:00:00Z", "duration_hours": 6,
  "search_start": "2024-05-11T00:00:00Z", "search_end": "2024-05-12T00:00:00Z"
}'
curl -s localhost:8000/assessments -H 'Content-Type: application/json' -d '{
  "mode": "replay", "cutoff": "2024-05-10T12:30:00Z",
  "eva_start": "2024-05-11T04:00:00Z", "duration_hours": 6,
  "search_start": "2024-05-11T00:00:00Z", "search_end": "2024-05-12T00:00:00Z"
}'
```

Запросы синхронные и сработают, если архив за период уже в хранилище. На пустом хранилище то же тело отправляют в
`POST /jobs`.

Разбор по архиву совпадает с `docs/examples/review_2024-05-11.zip`: 73 окна-кандидата, 38 исключены по
`critical`, рекомендовано 09:30–15:30.

Прогноз из прошлого совпадает с `docs/examples/replay_2024-05-11_cutoff_05-10T1230.zip`. Там интереснее:

- Линия SEP берёт вероятность S1 55 % из выпуска 12:30 и даёт `elevated` на весь период. Порог 50 % это наше
  правило (D42).
- На 111 минутах геомагнитного доступа линия даёт `high`. Это условная экспозиция (D47), тоже наше правило: витки
  известны заранее, а поток ещё не измерен. Обоснование обоих правил в
  [SCIENTIFIC_BASIS.md, «Уровни и данные»](SCIENTIFIC_BASIS.md#уровни-и-данные).
- Всё это `external_forecast` с уверенностью `low`: поток не измерен ни на одной минуте суток. Технический
  `reason` говорит об этом первой фразой, `explanation` второй, сразу после решения.
- В запрошенном окне 04:00–10:00 72 опасные минуты (`high + critical`), у лучших окон ноль. Рекомендация переносит
  выход на ближайшее к запрошенному чистое окно 09:30–15:30 (D49, наше правило).
- `verification` даёт заблаговременность 828 минут до первого факта ≥ `high` в 02:18. Попаданий 93 минуты,
  пропусков 14, ложных тревог 18. Выбор окна устоял: окно прогноза совпало с окном по факту.

Честная оговорка: правила D47–D49 и D79 сложились после разбора этого самого дня, 11 мая 2024. Поэтому пример
показывает, как правила работают, а не проверяет их на новых данных.

### Ответ расчёта

Мы сохраняем результат в `data/assessments/<id>.json`, и `GET /assessments/{id}` отдаёт его без изменений.

| поле | что значит |
|---|---|
| `id` | идентификатор расчёта, 12 шестнадцатеричных знаков |
| `created_at` | когда посчитано |
| `request` | запрос, как его принял сервис |
| `asof` | момент данных: время расчёта, момент отсечения или `null` в разборе по архиву |
| `algorithm_version` | версия кода и конфигов, например `03da709+cfg3d0acff4` |
| `trajectory` | провайдер, эпоха, `is_reconstruction`, провенанс, `age_at_query_hours`, точки трассы и `saa_passes` |
| `lines` | шесть линий риска, см. ниже |
| `requested_window` | оценка запрошенного окна |
| `windows` | оценки всех окон-кандидатов |
| `recommendation` | рекомендация окна, см. ниже |
| `sources_used` | откуда взяты числа: провенанс всех использованных записей |
| `data_availability` | `availability` по каждой линии |
| `limitations` | ограничения расчёта словами |
| `rules` | применённые правила сравнения окон и ограничения запроса |
| `verification` | только в `replay`, иначе `null`: сверка прогноза с фактом |
| `geometry` | страховка по геометрии доступа (D61) |

Точка трассы в `trajectory.samples` хранит время, широту, долготу, высоту, освещённость, магнитную широту, признак
ЮАА и уровень. `saa_passes` перечисляет проходы через ЮАА с правилом, значением и провенансом. Контур ЮАА 24 000 нТл
взят из Heirtzler 2002 и ждёт сверки человеком
([SCIENTIFIC_BASIS.md, «Что ещё взято из литературы»](SCIENTIFIC_BASIS.md#что-ещё-взято-из-литературы)).

#### Линии риска

В `lines` шесть линий: `sep_protons`, `proton_access_geometry`, `meteor_showers`, `conjunctions`, `dose_proxy`,
`illumination`.

| поле линии | что значит |
|---|---|
| `line`, `mechanism` | код линии и вид опасности |
| `intervals` | интервалы с `level`, `kind`, `rule`, `note`, `provenance` |
| `availability` | есть ли данные для линии |
| `confidence` | уверенность `grade` (`low`, `medium`, `high`) и от чего она зависит (`depends_on`) |
| `limitations` | ограничения линии словами |
| `metrics` | числовые показатели линии, например минуты доступа или неизмеренного потока |

Откуда уровни линии протонов. `elevated` ставится от S1 по шкале S NOAA. `critical` ставится по порогу NASA ESPE:
поток от 100 MeV не ниже 1 pfu. Оба опасных уровня ставятся только на минутах геомагнитного доступа (D63). Порог
`high` (от 30 MeV не ниже 1 pfu) уже наше правило, по аналогии с ESPE. Подробно это разобрано в
[SCIENTIFIC_BASIS.md, «Уровень и экспозиция»](SCIENTIFIC_BASIS.md#уровень-и-экспозиция-d63). Пороги метеоров и
запас по сближениям тоже наши правила, они собраны в разделе
[«Метеоры и сближения»](SCIENTIFIC_BASIS.md#метеоры-и-сближения) того же документа.

#### Оценка окна

`requested_window` и каждый элемент `windows` устроены одинаково.

| поле | что значит |
|---|---|
| `window` | границы окна `start`, `end` |
| `per_line` | часы каждого уровня по каждой линии штрафа |
| `completeness` | полнота данных в окне |
| `excluded_reason` | почему окно исключено, или `null` |

Штраф окна считается как `1.0 × часы(high + critical) + 0.25 × часы(elevated)`. Окно с `critical` исключается.
Окно, где по линии штрафа больше 15 минут без уровня, тоже исключается (D70). Веса, шаг и допуски это наши
правила, а не физика: стандарта выбора окна ВКД в открытых источниках нет. Перебор показал, что от весов и допусков
выбор окна не зависит ([SCIENTIFIC_BASIS.md, «Сравнение окон»](SCIENTIFIC_BASIS.md#сравнение-окон)).

#### Рекомендация

| поле | что значит |
|---|---|
| `preferred` | рекомендованное окно или `null` |
| `equivalents` | окна, равнозначные рекомендованному |
| `insufficient` | `true`, когда все окна исключены и оснований для выбора нет |
| `explanation` | объяснение обычными словами списком фраз; первая фраза это решение (D76) |
| `reason` | технический текст с кодами уровней и решений для аудита |
| `rules_applied` | правила выбора окна с кодами решений |

Порядок выбора тоже наш. Запрошенное окно остаётся, если оно равнозначно лучшим (D45). Иначе мы предлагаем окно
с минимумом опасных минут, а из таких ближайшее к запрошенному (D49). Равнозначность задают D79 и D56.

#### Сверка с фактом

Поле `verification` есть только в «Прогнозе из прошлого». Факт здесь это не независимое измерение, а тот же расчёт
по всем данным, опубликованным позже (D41). Ошибка модели доступа попала бы и в прогноз, и в факт; об этом
подробнее в [SCIENTIFIC_BASIS.md](SCIENTIFIC_BASIS.md#что-проверяет-проверка-после-события).

| поле | что значит |
|---|---|
| `predicted`, `observed` | интервалы линии `sep_protons` по прогнозу и по факту |
| `observed_preferred`, `observed_insufficient` | какое окно выбрал бы расчёт по факту |
| `lead_time_minutes`, `alarm_lead_time_minutes` | заблаговременность: от отсечения до первого факта ≥ `high` |
| `first_observed_alarm`, `first_predicted_warning`, `first_predicted_alarm` | первый факт ≥ `high` и первые предупреждения прогноза |
| `hit_minutes`, `miss_minutes`, `false_alarm_minutes` | попадания, пропуски и ложные тревоги по минутам периода поиска |
| `quiet_minutes`, `unverified_minutes`, `predicted_unknown_minutes` | спокойные минуты, минуты без факта, минуты без уровня в прогнозе |
| `exposure_hit_minutes`, `exposure_miss_minutes`, `exposure_false_alarm_minutes` | тот же счёт по минутам экспозиции экипажа |
| `requested_exposure_minutes`, `preferred_exposure_minutes` | минуты экспозиции по факту в запрошенном и рекомендованном окнах |
| `window_choice_stable` | устоял ли выбор: окно прогноза совпало с окном по факту или входит в равнозначные по факту (D65) |
| `baselines` | три бейзлайна на том же отсечении (D66): `persistence`, `single_alert`, `swpc_outlook` |
| `note` | пояснение сверки словами |

#### Геометрия доступа

Поле `geometry` информационное и рекомендацию не меняет (D61). Оно показывает, сколько минут трасса была бы открыта
для протонов при самой сильной буре по Kp. Смысл простой: вспышку за сутки не предсказать, а геометрию витков видно
заранее ([SCIENTIFIC_BASIS.md](SCIENTIFIC_BASIS.md#правила-добавленные-по-итогам-проверки-и-трёх-рецензий)).

| поле | что значит |
|---|---|
| `kp` | Kp, при котором считался доступ протонов |
| `requested_minutes`, `preferred_minutes` | минуты возможного доступа в запрошенном и рекомендованном окнах |
| `safest`, `safest_minutes` | самое закрытое окно среди рекомендованного и равнозначных и его минуты |
| `note` | пояснение словами |

## Сводка и вопросы экипажа

### Сводка для экипажа

Короткий ответ на вопрос «выходить, переносить или оснований нет и почему» по уже посчитанному расчёту (D58).
Главное свойство: **языковая модель формулирует, но не считает**.

```sh
curl -s 'localhost:8000/assessments/56780a932e72/briefing?question=summary' | jq -r '.text, .source'
```

Полная форма запроса: `GET /assessments/{id}/briefing?question=summary&language=ru&voice=false&refresh=false`.

| параметр | по умолчанию | что значит |
|---|---|---|
| `question` | `summary` | быстрый вопрос: `summary`, `can_go_now`, `when_better`, `what_blocks` |
| `language` | `ru` | язык; поддержан только `ru` |
| `voice` | `false` | синтезировать речь, см. [Озвучка](#озвучка) |
| `refresh` | `false` | собрать сводку заново вместе со звуком |

Сводка кешируется рядом с расчётом, в `data/assessments/<id>.briefing.<вопрос>.<язык>.json`. `refresh=true`
собирает её заново. Шаблонную сводку после отказа модели мы навсегда не храним: при подключённой модели она
соберётся заново.

Быстрые вопросы задаются кнопками. Каждый из них это другой акцент на тех же фактах. Вопрос своими словами описан
[ниже](#свой-вопрос). Распознавания речи в API нет: голосовой ввод своего вопроса делает страница средствами
браузера (D90) и присылает в API уже текст.

Ответ сводки:

| поле | что значит |
|---|---|
| `text` | текст сводки для экрана |
| `speech_text` | тот же смысл для синтезатора речи: без цифр и латиницы |
| `source` | `llm` это текст модели с проверенными числами, `template` это шаблон из тех же фактов |
| `model` | имя модели, например «Qwen 3.8»; `null` без модели |
| `validated` | прошёл ли текст автоматическую проверку |
| `violations` | нарушения проверки и причина, по которой ответил шаблон |
| `facts` | факты, из которых собран текст, и список разрешённых значений `allowed_values` |
| `facts.verdict` | вердикт: `keep_requested` окно остаётся, `move_to` перенос, `insufficient` оснований нет |
| `audio_url` | путь к WAV или `null` |
| `voice_error` | почему звука нет; `null`, когда всё в порядке |
| `asked` | текст своего вопроса; у обычной сводки `null` |
| `assessment_id`, `question`, `language`, `algorithm_version`, `generated_at`, `style` | к чему относится сводка, когда собрана, версия речевого стиля |

### Как собирается текст

1. Факты собираются из сохранённого `AssessmentResult` детерминированно, без модели. Туда входят вердикт (окно
   остаётся, перенос, оснований нет), запрошенное и рекомендованное окно и опасные минуты в каждом. Ещё отрезки
   этих минут с линией и уровнем и момент, после которого их в периоде поиска нет. И наконец пробелы данных,
   отключённые источники, уверенность линии протонов, провенанс и список разрешённых значений.
2. Модель (Qwen 3.8 через Cloud.ru Evolution, совместимый с OpenAI) получает только этот список и пишет текст.
   Если ключей Qwen на сервере нет, вызов может идти через ретранслятор на компьютере команды
   (`EVARISK_LLM_RELAY_URL`, D91).
3. Каждое число, время и дата текста сверяются со списком фактов. Проверяются и слова вердикта, и основание данных
   («по данным на …» для прогноза из прошлого). Длина не больше 70 слов, последняя фраза «Решение за руководителем
   работ.».
4. При нарушении модель один раз получает перечень нарушений. Если и второй текст не прошёл, отвечает шаблон из
   тех же фактов.
5. Временный сбой вызова (сеть, таймаут, коды 408, 409, 429 и 5xx) повторяется до 5 раз с растущей паузой
   (`QWEN_RETRIES`). Через ретранслятор повторов до 2. Когда попытки кончились, отвечает шаблон с этой причиной.
6. Без ключей модели и без ретранслятора сервис всегда отвечает шаблоном. Это штатное состояние, а не ошибка, и
   оно покрыто тестами.
7. `speech_text` строится из выданного текста детерминированно. Время и единицы пишутся словами: «04:39» это
   «четыре тридцать девять», «18 мин» это «восемнадцать минут». `UTC` это «по всемирному времени», коды линий
   по-русски. Ни цифр, ни латиницы: синтезатор речи пропускает их молча.

### Свой вопрос

Кроме четырёх быстрых вопросов, сводке можно задать вопрос своими словами: `POST /assessments/{id}/briefing/ask`.
На странице это поле под кнопками.

```sh
curl -s -X POST localhost:8000/assessments/56780a932e72/briefing/ask -H 'Content-Type: application/json' \
  -d '{"text": "а если выйти в 08:00?"}' | jq -r '.text, .source'
```

| поле тела | что значит |
|---|---|
| `text` | вопрос, от 1 до 300 знаков |
| `language` | язык, по умолчанию `ru` |
| `history` | необязательно: до трёх пар `{"asked", "answer"}` от старой к новой, ответ до 1000 знаков |

Вопрос вставляется в запрос к модели как данные, а не как указание. Модель получает факты сводки и факты вопроса
(D89). Это причина выбора окна и окна рядом с временами и сдвигами из вопроса («в 08:00», «на час позже»). Туда же
идут окна в пределах часа от запрошенного и рекомендованного начала, с минутами по видам опасности и причиной
исключения. Ещё модель видит тень и опасные отрезки в обоих окнах и надёжность оценок.

Первая фраза ответа отвечает на вопрос. Проверка та же, что у сводки: числа, времена, запреты, основание данных и
последняя фраза. Отличий два: вердикт первой фразой не нужен, а длина до 90 слов. Текст, не прошедший проверку, мы
не показываем. Тогда ответ начинается с «На этот вопрос проверенного ответа нет. Общая сводка.», дальше идёт общая
сводка, а причина названа в `violations`. Без модели свой вопрос остаётся без ответа, и сервис так прямо и
говорит.

`history` передаёт модели прошлые вопросы этого разговора как данные. Больше трёх пар это 400. Ответ приходит тем же
объектом, что и сводка, текст вопроса лежит в `asked`. В кеш он не пишется.

### Озвучка

Озвучка это необязательный параметр `voice=true`, по умолчанию выключена: оператору за столом она не нужна. Сервер
синтезирует речь, только если задан `EVARISK_TTS_URL`. Служба синтеза лежит в каталоге `tts/` и описана там. Без
неё `audio_url` пуст, `voice_error` называет причину, а страница читает `speech_text` средствами браузера.

Готовый звук отдаёт `GET /assessments/{id}/briefing/audio?question=&language=`: WAV, если озвучка запрашивалась и
служба синтеза настроена, иначе 404.

Сводка входит в выгрузку файлом `briefing.md`. В `result.json` её нет, ответ расчёта не меняется.

### Подключение внешнего терминала

Скафандр, бортовой планшет или другой потребитель получает ту же сводку одним из двух способов. Он либо опрашивает
`GET /briefing/latest`, либо принимает тот же JSON доставкой.

`GET /briefing/latest?voice=` отдаёт сводку `summary` последнего расчёта в режиме «Сейчас». Параметры `voice`,
`language` и `refresh` значат то же, что у сводки. Пока нет ни одного расчёта в режиме «Сейчас», ответ 404 с
объяснением.

Поля, которые нужны терминалу:

| поле | что с ним делать |
|---|---|
| `text` | показать на экране, это то же, что видит оператор |
| `speech_text` | отдать синтезатору речи: цифр и латиницы в нём нет |
| `audio_url` | готовый WAV или `null`; путь относительный, его отдаёт тот же сервис |
| `source` | `llm` это текст модели с проверенными числами, `template` это шаблон из тех же фактов |
| `validated` | прошёл ли текст автоматическую проверку чисел |
| `voice_error` | почему звука нет; `null`, когда всё в порядке |

```
curl -s http://localhost/briefing/latest | jq -r '.text, .speech_text, .source, .validated'
```

## Источники

### Состояние источников

```sh
curl -s localhost:8000/sources | jq '.[] | {name, state, last_success_at, records}'
```

`GET /sources` перечисляет источники с адаптером опроса и архивные источники. У архивного записи импортированы из
зеркала архивов, а адаптера обновления нет.

| поле | что значит |
|---|---|
| `name` | имя источника, например `nasa_oem` или `goes_sgps` |
| `products` | продукты источника |
| `cadence_s` | период опроса в секундах; у архивного источника `null` |
| `archive_only` | `true` у архивного источника |
| `supports_archive` | умеет ли источник отдавать архив |
| `state` | `active`, `frozen` или `disabled` |
| `reason`, `changed_at` | причина и время последней смены состояния |
| `last_attempt_at`, `last_success_at`, `last_error` | последняя попытка, последний успех, последняя ошибка |
| `last_record_fetched_at` | когда получена последняя запись |
| `records` | число записей в хранилище |

`active` значит, что источник опрашивается. `frozen` не опрашивается, но его записи в расчётах используются.
`disabled` выключает источник совсем: его записи расчёт не читает.

Сменить состояние можно так, причина обязательна:

```sh
curl -s localhost:8000/sources/donki/state -H 'Content-Type: application/json' \
  -d '{"state": "frozen", "reason": "проверка деградации"}'
```

В ответ приходит обновлённая строка источника. Неизвестный источник без записей в хранилище даёт 404.

`POST /sources/{name}/refresh` ставит задание на принудительное получение данных и отвечает 202 с `job_id`. Ход и
итог видны в `GET /jobs/{id}`. Для замороженного или отключённого источника задание завершается отказом с текстом.
Архивный источник даёт 409 `archive_only`, неизвестный 404.

Через публичный туннель Cloudflare состояние источников не меняется. `POST /sources/{name}/state` и
`POST /sources/{name}/refresh` тогда отвечают 403 `tunnel_readonly`. Запрет снимает настройка
`EVARISK_TUNNEL_READONLY` (по умолчанию `true`).

### Сырые записи: откуда взято число

Каждое число ответа ссылается на сырую запись через `provenance.raw_id`, и эту запись можно открыть.

```sh
curl -s localhost:8000/evidence/141ca0e1efcae4effb15855f | jq '.record'
```

| поле | что значит |
|---|---|
| `record` | запись индекса: `source`, `product`, `url`, `fetched_at`, `published_at` и `published_at_kind`, `data_version`, `sha256`, размер и тип |
| `content_text` | содержимое текстом, если запись текстовая и не больше 2 МБ, иначе `null` |
| `download_url` | адрес байтов записи, `/evidence/{raw_id}/download` |

`GET /evidence/{raw_id}/download` отдаёт байты записи с её исходным типом. Неизвестный `raw_id` даёт 404.

В ответе расчёта у `provenance` поля `raw_id`, `source`, `product`, `published_at`, `published_at_kind`,
`data_version`, `url`.

### Орбита, траектория и сближения

Эти три адреса риски не считают. Они отдают данные для карты и панели сближений.

#### Траектория

`GET /trajectory?start&end&step_minutes&mode` строит траекторию по OEM без линий, для фронтенда.

```sh
curl -s 'localhost:8000/trajectory?start=2024-05-11T00:00:00Z&end=2024-05-11T06:00:00Z&step_minutes=5&mode=review'
```

| параметр | что значит |
|---|---|
| `start`, `end` | интервал от 1 минуты до 48 часов, время с часовым поясом |
| `step_minutes` | шаг сетки от 1 до 10 минут, по умолчанию 1 |
| `mode` | `current` (по умолчанию) или `review`; `replay` здесь нет |

В ответе те же поля, что у `trajectory` расчёта, и `limitations`. `level` у всех точек `unknown`. Интервал вне
границ даёт 400, отсутствие эфемериды 409.

#### Орбита

`GET /orbit/latest` отдаёт OMM последней записи CelesTrak GP, чтобы браузер считал SGP4 сам. Там же заголовок
последнего OEM с провенансом.

| поле | что значит |
|---|---|
| `omm` | элементы орбиты OMM; без записи `null` |
| `provenance` | откуда взята запись CelesTrak; без записи `null` |
| `oem` | `creation_date`, `start_time`, `stop_time` и `provenance` последнего OEM; без записи `null` |

#### Сближения

`GET /conjunctions/latest` отдаёт последний отчёт SOCRATES по МКС независимо от расчёта. Отчёт относится к моменту
своего расчёта и следующим 7 суткам. К историческим датам он не применяется: архива SOCRATES нет (D29, D30).

| поле | что значит |
|---|---|
| `available` | есть ли отчёт; без отчёта `false` |
| `data_as_of` | время расчёта отчёта |
| `age_hours`, `stale`, `max_report_age_hours` | давность и признак устаревания: отчёт старше 24 часов устарел |
| `interval_start`, `interval_stop` | интервал отчёта, 7 суток |
| `conjunctions` | сближения: время, объект, расстояние, скорость, `max_probability` и уровень по MAXPROB |
| `coorbiting_rows` | число строк со-орбитальных объектов, в список они не входят |
| `limitations` | ограничения словами |
| `provenance` | откуда взят отчёт |

Уровень строки ставится по MAXPROB, то есть по верхней оценке вероятности столкновения. Пороги 1·10⁻⁵ и 1·10⁻⁴
взяты из правил полёта МКС по публикации NASA
([SCIENTIFIC_BASIS.md, «Что ещё взято из литературы»](SCIENTIFIC_BASIS.md#что-ещё-взято-из-литературы)).
Человеком они ещё не сверены, это отмечено в таблице
[«Все параметры слоя 1»](SCIENTIFIC_BASIS.md#все-параметры-слоя-1). Срок 24 часа и отсев со-орбитальных объектов по
скорости ниже 0.1 км/с это наши правила (D53).

Нечитаемая последняя запись CelesTrak GP или SOCRATES даёт 500 `bad_record`.

## Выгрузка

`GET /assessments/{id}/export` отдаёт zip-архив `evarisk_<id>.zip` по сохранённому расчёту.

```sh
curl -s -o evarisk.zip localhost:8000/assessments/56780a932e72/export
```

Внутри пять файлов:

- `result.json`: тот же объект, что возвращает API, в JSON с отступами;
- `report.md`: отчёт для чтения человеком;
- `briefing.md`: сводка для экипажа; если сохранённой сводки нет, кладём шаблонную из тех же фактов;
- `sources.json`: провенанс записей, на которые опирается расчёт;
- `timeline.csv`: интервалы всех линий, столбцы `line`, `start`, `end`, `level`, `kind`, `rule`.

Готовые архивы для примеров лежат в `docs/examples/`.

## Документация и служебные адреса

| адрес | что отдаёт |
|---|---|
| `GET /docs`, `GET /redoc` | интерактивное описание API с примерами |
| `GET /openapi.json` | машиночитаемая схема API |
| `GET /manual` | список документов: `name` и `title` (заголовок первого уровня) |
| `GET /manual/{name}` | текст документа в Markdown |
| `GET /rules` | правила окон и параметры линии SEP из конфигов с источниками параметров |
| `GET /health` | `status`, `raw_root`, `worker_last_tick` (время последнего тика воркера или `null`) |

`/manual` отдаёт `README.md`, `CONTRIBUTING.md` и `docs/*.md`. Имя документа из `docs/` пишется без каталога,
например `API.md`. Шаблон README модуля в список не входит, а путь вне каталога даёт 404. Раздел «Документация»
страницы и пояснения к терминам ссылаются сюда.

```sh
curl -s localhost:8000/manual/API.md | head
```

`/rules` питает экран настроек страницы. В нём три части: `windows` (правила окон), `sep` (параметры линии SEP) и
`sources` (источники параметров). У правил окон источника нет, потому что это наше правило; там `null`.

Страница сервиса открывается на «/». Если сборка фронтенда есть, старая страница доступна на «/dev».

## Ошибки

Ошибка приходит как `{"error": {"code": "…", "message": "…"}}`. В `message` причина объяснена по-русски.

| HTTP | `code` | когда |
|---|---|---|
| 400 | `validation` | тело или параметры не прошли проверку, например период допустимого начала вне границ |
| 400 | `unknown_question`, `unknown_language` | неизвестный быстрый вопрос или язык сводки |
| 400 | `empty_question` | пустой текст своего вопроса |
| 403 | `tunnel_readonly` | смена состояния или обновление источника через туннель Cloudflare |
| 404 | `not_found` | нет расчёта, задания, записи, документа, озвучки или расчёта в режиме «Сейчас» |
| 409 | `no_trajectory` | нет эфемериды МКС, доступной на момент данных и покрывающей период с запасом в час |
| 409 | `archive_only` | обновление архивного источника |
| 413 | `too_large` | тело запроса больше 262 144 байт |
| 500 | `bad_record` | последняя запись CelesTrak GP или отчёт SOCRATES не разобраны |

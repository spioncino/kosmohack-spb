# windows

Назначение: окна-кандидаты одинаковой длительности, часы пересечения с интервалами линий, правила предпочтения, явно заданные ограничения условий работ и рекомендация.

## Интерфейс
- `candidates`, `overlap_hours`, `score`, `penalty`, `equivalent`, `summarize_exclusions`, `recommend` в `compare.py`, часы по уровням в `measures.py`, объяснение в `explain.py`; правила в `config/windows.toml`.
- Порядок выбора (D49): ранжирование по минутам `high + critical`, затем по штрафу, затем по началу; запрошенное окно сохраняется при равнозначности лучшему (D45, D48), при этом если равнозначны все допустимые окна, причина добавляет «обстановка на периоде поиска однородна: ни одно допустимое окно не лучше запрошенного»; иначе перенос идёт на окно из `clean` (минимум минут `high + critical`, штраф в пределах допуска), ближайшее к запрошенному старту, при равенстве раньше начинающееся; причина «запрошенное окно хуже: минут high+critical 18 против 0, штраф … против …; выбрано ближайшее к запрошенному из N окон с минимумом таких минут (D49)»; для исключённого запрошенного окна «запрошенное окно исключено; выбрано ближайшее к нему …». Без запрошенного окна берётся первое по ранжированию.
- Полнота и неизвестные минуты (D56): `completeness` это доля минут окна с известным уровнем, усреднённая по линиям штрафа; `unknown_hours(s)`; ранжирование `(минуты high+critical, часы без уровня, штраф, начало)`; `equivalent` требует ещё разницу часов без уровня не больше шага сетки (и равные целые минуты high+critical, D79); `clean` это окна с минимумом и тех и других.
- Когда допустимых окон нет, причина рекомендации это `summarize_exclusions(scores)`: «все N окон исключены: critical по линии sep_protons в K окнах из N (0.05–0.48 ч); нет данных по линии conjunctions (missing) в N окнах из N; …» (группировка по линии и виду причины, остальные причины по тексту со счётчиком), а не перечисление `excluded_reason` каждого окна.
- Равнозначность (D79, уточняет D48): `equivalent(s, best, rules)` истинно, когда у окна столько же целых минут `high + critical` (часы `exposure_hours` по всем линиям штрафа, округлённые до минуты), сколько у лучшего, разница штрафа не больше `equivalence_tolerance_hours` и разница часов без уровня не больше одного шага сетки (D56). Окно с 7 мин `high` не равнозначно окну без них, даже если это меньше шага сетки и штраф в пределах допуска. По ней строятся `equivalents` и сохранение запрошенного окна (D45). Причина рекомендации называет штраф и минуты high+critical запрошенного и лучшего: «перенос не улучшает: …; D45, D79)» при равнозначности, «запрошенное окно хуже: минут high+critical 7 против 0, …» при переносе; хвост «равнозначными по D79 (те же минуты high+critical, штраф в пределах допуска) считаются ещё N». В `rules_applied` правило записано словами: «окно с critical исключается» (или «не исключается»).
- Отсечение (D80): `score(..., cutoff=None)`; при заданном `cutoff` окно со стартом раньше него исключается с причиной `measures.BEFORE_CUTOFF_REASON` «окно начинается раньше момента отсечения» (на момент прогноза оно уже в прошлом); окно со стартом ровно в момент отсечения допустимо. `summarize_exclusions` считает такие окна отдельной группой «окно начинается раньше момента отсечения в K окнах из N».
- `recommend` ранжирует допустимые окна по ключу (минуты `high + critical`, часы без уровня, штраф, начало окна); часы и штраф округляются до `PENALTY_DIGITS` = 9 знаков (1e-9 ч): часы суммируются по интервалам в float, и при равных по смыслу штрафах сумма отличается на 1e-15 ч в зависимости от разбиения интервалов; без округления такой шум выбирал бы не самое раннее из равнозначных окон. Допуск равнозначности `equivalence_tolerance_hours` считается по неокруглённому штрафу.
- `Constraints(Frozen)` (D43): `min_sunlit_fraction: float | None` в `[0, 1]` (иначе `ValidationError`), `start_in_daylight: bool = False`; свойство `any_set`. Схема запроса API реэкспортирует этот класс.
- `score(window, assessments, rules, constraints=None, illumination=None)`: `per_line` и `completeness` только по `assessments` (линии штрафа); при заданных ограничениях и линии освещённости (`LineAssessment` линии `illumination`) к `excluded_reason` добавляется «ограничение освещённости: доля света 0.43 < 0.60» (доля это часы `none` к часам `none + elevated` линии в окне) или «ограничение освещённости: старт в тени» (уровень интервала, содержащего `window.start`); без линии, при `availability != available` или без интервалов на окне «ограничение освещённости: данных об освещённости в окне нет». Линия освещённости в `per_line` не входит и штраф не меняет.
- `constraint_rules(constraints) -> tuple[str, ...]`: строки для `rules` ответа, по одной на заданное ограничение; `()` без ограничений.
- `sunlit_fraction(window, illumination) -> float | None`, `starts_in_daylight(window, illumination) -> bool | None`, `illumination_reasons(window, constraints, illumination) -> list[str]`.

- `explain.explain(scores, rec, requested) -> tuple[str, ...]` (D76, D78): объяснение рекомендации обычными словами, `recommend` кладёт его в `Recommendation.explanation`. Первая фраза это решение: «Рекомендуем перенести выход на 10:45–16:45 UTC, на 2 ч 15 мин раньше.», «Рекомендуем оставить запрошенное окно 18:00–00:00 UTC: перенос заметного выигрыша не даёт.» или «Подходящего окна нет: исключены все 2 окна.». `span_text` пишет окно до полуночи без дат («18:00–00:00 UTC»), окно через полночь с днями («22:00 10 мая – 04:00 11 мая UTC»). Дальше опасные минуты (`high` и `critical`) и минуты повышенного фона (`elevated`), по строке на линию с длительностью по-человечески (`duration_text`: «4 ч 42 мин») и тем, что уровень значит (`DANGER_MEANING`, `RAISED_MEANING`): «Протоны: в запрошенном окне 4 ч 42 мин, в новом 2 ч 27 мин. Протонов больше обычного, но …». «Зато в новом окне меньше повышенного фона:» стоит только при меньшей сумме минут, иначе «Повышенный фон в окнах:». Потом минуты без данных, «Среди окон, где опасность наименьшая, это ближайшее к запрошенному.» (`NEAREST`) и «Ещё 3 окна почти равноценны выбранному.»; сохранённое окно с опасными минутами получает «Меньше опасных минут нет ни в одном подходящем окне.» (D79); при отсутствии окон причины исключения сгруппированы: «В 38 окнах из 73 критический уровень протонов.», «Во всех 73 окнах мало света.». `before_tail` вставляет фразу перед выбором ближайшего окна и числом равноценных (так api добавляет опасные отрезки и линии вне сравнения окон). Коды уровней, линий, решений и слово «штраф» остаются только в `reason`. `plain_reason` переводит причину исключения окна («критический уровень протонов, всего 1 ч 14 мин», «нет данных по сближениям», «мало света: на свету 43% окна, а задано не меньше 60%»), `plural` склоняет слово после числа, `line_name` даёт русское название линии, `cap` поднимает первую букву, не трогая остальные.
- Минуты по линиям (D84): линии идут одновременно, и сумма их минут бывает больше окна (разбор 8 июня 2024: протоны и метеоры повышены всё окно 6 ч, сумма 720 мин). `explain` называет числами только минуты каждой линии: «В новом окне опасных минут нет:» и «В новом окне опасных минут меньше:» со строками по линиям, «Опасные минуты в окне, по каждой линии отдельно:», «Опасных минут в обоих окнах поровну: протоны 40 мин.», «Минуты без данных:» со строками «Протоны: в запрошенном окне 10 мин, в новом нет.»; суммы решают только, какое окно лучше. Числа технического `reason` остаются суммами и подписаны честно: `SUM_DANGER` «линия-минут high+critical (сумма по линиям)», `SUM_ELEVATED`, `SUM_UNKNOWN`; ранжирование и штраф не менялись.
- Ноль по прогнозу (D84): `explain.forecast_zero(explanation, requested, chosen)` дописывает к «Опасных минут в окне нет.», «Опасных минут нет ни в запрошенном, ни в новом окне.» и «В новом окне опасных минут нет» оговорку «но это по прогнозу, измерений потока протонов нет» (или «частью по прогнозу, поток протонов измерен не всё время»); фраза остаётся на своём месте и начинается как прежде. Состояние окна даёт `measures.unmeasured_state` по `measures.unmeasured_flux_minutes(window, intervals)`: минуты окна под интервалами линии протонов с отметкой «поток: нет отсчёта» или «поток: внешний прогноз вероятности» (`UNMEASURED_FLUX_NOTES`). Вызывает `api.service.with_notes`.
- `measures.py`: `exposure_hours`, `elevated_hours`, `unknown_hours`, шаблоны причин исключения (`CRITICAL_REASON`, `MISSING_REASON`, `GAP_REASON`, `SUNLIT_REASON`) и константы освещённости; их используют и `compare`, и `explain`.

## Инварианты
- Окно, где по линии штрафа больше одного шага сетки без уровня, исключается с причиной «пробел данных по линии X: N мин без уровня (D70)»; `summarize_exclusions` группирует такие причины по линии.
- Уровни линий не сливаются в один индекс: `per_line` хранится раздельно, окно с `critical` по любой линии и окно без данных по любой линии исключаются (D28). Ранжирование допустимых окон это взвешенная сумма часов по линиям штрафа (`penalty`, `exposure_hours`), правило выводится в `rules_applied`.
- Правила выводятся пользователю как `rules_applied`; заданные ограничения освещённости попадают в `rules` ответа через `constraint_rules`.
- Изменение длительности это новый набор кандидатов, а не пересчёт старого.
- Освещённость это условие работ, не опасность (D43): тень не штрафуется, окно исключается только по явно заданному ограничению; отсутствие данных об освещённости при заданном ограничении исключает окно, а не пропускает его.

## Как тестировать
- `uv run pytest tests/unit/test_explain.py -q`: объяснение для переноса по повышенному фону (случай 10 мая: 13:00 → 10:45, «на 2 ч 15 мин раньше»), по опасным минутам, для сохранения окна, для исключённого запрошенного окна и для отсутствия окон; в объяснении нет кодов уровней, линий, решений и слова «штраф».
- `uv run pytest tests/unit/test_windows.py -q`: синтетическая освещённость свет 0–3 ч, тень 3–6 ч, свет 6–24 ч; окно 0–6 ч с порогом 0.6 исключается с «доля света 0.50 < 0.60», с порогом 0.5 допустимо; окно со стартом в 3 ч при `start_in_daylight` исключается «старт в тени»; ограничение без линии или вне её интервалов даёт «данных об освещённости в окне нет».

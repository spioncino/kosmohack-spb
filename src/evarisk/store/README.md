# store

Назначение: сырое хранилище ответов источников, неизменяемое, с индексом на диске. Это источник истины и единственное хранилище данных: разобранных таблиц нет, виды `views*` разбирают сырое при каждом чтении, поэтому команды `make reindex` нет (примечание к D4); в Postgres только `jobs` и `source_state`.

## Интерфейс
- `views.unreadable_records(asof, start, end) -> list[UnreadableRecord]`: записи, отвергнутые разбором при чтении слоя (`raw_id`, `source`, `product`, `available_at`, `reason`), с доступностью в `[start − 7 суток, end]` и не позже `asof.t`. Отказ разбора одной записи (3-day forecast, geomag_forecast, daypre, kp_forecast, kp_1m, суточный файл GOES SGPS, OEM, GFZ Kp) не останавливает чтение: запись пропускается, причина сохраняется в `AsOf.unreadable` и отдаётся этой функцией для ограничений результата. Запись без известного времени доступности к периоду не отнесена и в список не попадает.
- `AsOf.unreadable: dict[str, UnreadableRecord]` и `AsOf.mark_unreadable(record, reason)`: накопитель отказов разбора у вида на момент; `views.read_parsed(asof, record, parse)` и `views.read_cached(asof, record, cache, parse)` разбирают одну запись и пишут туда причину отказа.
- Чтение сужено по периоду запроса: `views_kp._three_day_issues(asof, start, end)` и `proton_event_probability` читают выпуски с доступностью в `[start − 4 суток, end + 4 суток]` (`FORECAST_MARGIN`); `views._goes_series` читает суточные файлы GOES за сутки периода ± 1 сутки, определяя сутки по имени в url (`_d20240510_`), потому что у переобработанного файла доступность позже суток наблюдения. Запас периода задаёт вызывающий код.
- `RawStore.amend_availability(raw_id, published_at, kind, reason)`: исправление времени доступности записи со следом в `notes` (содержимое неизменно); файл индекса заменяется целиком через временный файл в том же каталоге и `os.replace`, поэтому прерванная перезапись оставляет прежний файл, а не обрезанный (имя временного файла не оканчивается на `.jsonl` и в подпись индекса не входит); `mirror_import.classify(rel, content, last_modified)` и `import_mirror` берут Last-Modified из манифеста (S3 у OEM, HTTP NCEI у GOES SGPS) и исправляют уже импортированные записи (`ImportSummary.amended`, D57, D69). `views_kp.kp_forecast(..., include_elapsed=True)` оставляет интервалы, истёкшие к отсечению (D54).
- `RawStore(root, disabled=frozenset())` и `RawStore.without(sources) -> RawStore`: вид того же хранилища без записей отключённых источников (`records` их не возвращает, `get` и `read` по `raw_id` работают); так состояние `disabled` исключает источник из расчётов (D51).
- `views.message_provenance(record, issued_at, message_id)`: провенанс сообщения внутри агрегатной записи со временем выпуска сообщения (D50); используется для пересечений, окончаний и прогнозов прихода CME DONKI, GST в `kp_as_known` и утверждения DONKI в бейзлайне.
- `RawStore(root).put(...) -> (RawRecord, created)`: сохраняет байты и строку индекса; повтор того же url и содержимого не дублируется. Параметр `data_version` обязателен (D20).
- `get(raw_id)`, `read(raw_id)`, `records(source, product)`. Индекс читается с диска заново, когда набор или размер файлов `index/*.jsonl` изменился: записи, дописанные воркером, видны в процессе API без перезапуска (D2); свой `put` обновляет кеш и подпись без перечитывания.
- `RawRecord`: провенанс записи; `published_at`, `published_at_kind` и `data_version` заполняет адаптер из самого продукта.
- `AsOf(store, t)`: вид на момент `t` (D5, раздел 4.3 спеки). `records(source, product=None)` при конечном `t` оставляет только записи с `published_at <= t`, записи с `published_at_kind == "unknown"` исключаются; `t is None` означает разбор без ограничения. Порядок по `(published_at, fetched_at)`; `latest(source, product)` последняя запись в этом порядке; `read(record)` байты записи.
- `views.provenance_of(record) -> Provenance`.
- `views.oem_for(asof, window) -> (OemEphemeris, RawRecord) | None`: самая поздняя по доступности запись `nasa_oem/oem`, чья эфемерида покрывает окно с запасом в час с каждой стороны; разбор кешируется по `raw_id`.
- `views.proton_series(asof, start, end) -> ProtonSeries | None`: записи `goes_sgps/sgps_l2_avg5m`, по одной на сутки (самая поздняя по доступности), отсчёты в `[start, end)`. `p10`, `p30`, `p50`, `p100` в pfu через `integral_flux_pfu` (D19, `kind="computed"`; `p30` нужен линии SEP, D36), `energies_mev` 13 эффективных энергий каналов (среднее по двум датчикам геометрического среднего границ), `diff_flux` формы `(N, 13)` в protons/(cm² sr MeV s), среднее по датчикам; спектр целиком нужен прокси дозы (D34).
- `views.proton_series` в текущем режиме (P2-9): записи `swpc_live/protons_7d` (JSON `integral-protons-7-day.json`, `published_at = fetched_at` derived) дают `p10`/`p30`/`p50`/`p100` напрямую из строк с энергиями `>=10/30/50/100 MeV`, `kind="observation"`, `data_version="swpc live integral"`, `note` «официальные интегральные потоки SWPC (GOES primary), спектра нет», `energies_mev` формы `(0,)` и `diff_flux` формы `(N, 0)`; отсутствующая энергия в отсчёте это `NaN`. Записи читаются от поздней к ранней, поздняя перекрывает раннюю по `time_tag`, чтение останавливается на записи, чей первый отсчёт не позже `start`; записи, полученные до `start`, не читаются. Если за интервал есть и суточные файлы GOES, и живые записи, GOES приоритетнее за покрытые им сутки, живые отсчёты дополняют остальные сутки: строки спектра у них `NaN`, `kind="computed"`, `data_version` перечисляет обе версии, `note` называет сутки GOES и подписи обеих частей. Без живых записей поведение прежнее.
- `views.kp_series(asof, start, end) -> KpSeries | None`: из последней доступной записи `gfz_kp/kp` (D21: `definitive`, в replay не участвует), интервалы с началом в `[start - 3h, end]`, `kind="observation"`.

`AsOf` единственный путь чтения для `risk/`, `windows/`, `replay/`; `views` возвращает `None`, когда данных нет, и никогда не подставляет значения.
- `mirror_import.import_mirror(mirror_root, store) -> ImportSummary(imported, skipped, unknown_version, amended, unrecognized, unrecognized_names)`: строка манифеста, на которой `classify` или чтение файла дали `ValueError`, `KeyError` или `OSError` (заглушка HTML вместо JSON DONKI, неизвестный раздел или продукт NCEI, пропавший файл), пропускается: импорт остальных строк идёт, счётчик в `unrecognized`, первые три имени с причиной в `unrecognized_names`, а `backfill.BackfillReport.notes()` называет их строкой «файлов зеркала не распознано: N, первые: …». импорт зеркала `data/mirror` (D33) по `manifest.jsonl`; `fetched_at`, `url`, `content_type`, `status` берутся из манифеста, а не из момента импорта. `classify(rel, content) -> Classified` определяет `source`, `product`, `published_at`, `kind`, `data_version` по первому сегменту пути: NCEI (`swpc_archive`) по строке `:Issued:` (`exact`, `issue HHMM` у 3-day и discussion, иначе `daily`; без строки `:Issued:` запись `unknown` с `data_version="no-issued"`, считается в `unknown_version`); OEM по `CREATION_DATE` (`exact`, `oem <дата>`); GOES SGPS позднее из следующих суток 00:05Z и HTTP Last-Modified файла из манифеста (`mirror_import.goes_availability`: файл NCEI за 10 мая 2024 появился 17 мая 05:06:54; `derived`, `reprocessed <версия из имени>`, D22, D69), `notes` называет правило, давшее время, а без Last-Modified остаётся следующие сутки 00:05Z с пометкой, что время появления файла неизвестно; DONKI наибольший `messageIssueTime` (`derived`); GFZ 2024-07-15T00:00Z (`derived`, `definitive`, D21); документы по метеорам и страница SEP `unknown`. Повторный запуск ничего не дублирует: `put` возвращает `created=False`, запись считается в `skipped`. Запуск: `make import-mirror` или `scripts/import_mirror.py --mirror <каталог>` с `EVARISK_RAW_ROOT`.

## Инварианты
- Файлы и строки индекса никогда не изменяются и не удаляются кодом.
- `published_at is None` только при `published_at_kind == "unknown"`; такие записи непригодны для replay.
- `raw_id` детерминирован: пересоздание хранилища из тех же ответов даёт те же id.
- У каждой записи есть `data_version`: версия продукта (номер выпуска, версия файла, дата снимка).

## Как тестировать
- `uv run pytest tests/store -q`, всё на `tmp_path`, без сети и базы.

## Чего не делать
- Не парсить содержимое здесь; разбор в `parsers/` и `orbit/`.
- Не выдумывать `published_at`: если продукт не содержит времени выпуска, ставить `unknown` или `derived` с пояснением в `notes`.

## Kp как знали тогда и прогноз Kp (P2-5, D39)
- `AsOf.aggregates(source, product)`: записи без фильтра по `t` (записи с `published_at is None` исключены) для агрегатов, элементы которых датированы по отдельности; вызывающий обязан отбирать элементы по их собственному времени `<= t`. Единственный пользователь: `views_kp.kp_as_known` с DONKI (недельные агрегаты, `published_at` = последнее сообщение недели).
- `KpSeries.notes: tuple[str, ...]`: по одной подписи на интервал (источник значения); у GFZ пусто.
- `views_kp.kp_as_known(asof, start, end) -> KpSeries | None`: `kind = observation`, `data_version = "swpc dated products"`, интервалы с началом в `[start − 3h, end]`; приоритет источников: прошедшие к моменту выпуска ячейки таблицы 3-day forecast (поздний выпуск перекрывает ранний), затем DONKI GST по `messageIssueTime <= t` (позднее сообщение перекрывает раннее), затем «greatest observed 3 hr Kp over the past 24 hours» на восемь интервалов до выпуска (заполняет только пустые интервалы, поздний выпуск первым). Интервал без источника отсутствует в ряду, не подставляется.
- `views_kp.kp_forecast(asof, start, end)`: выпуски прогноза Kp (архивные 3-day и geomag_forecast, живые 3-day и снимки kp_forecast) сливаются по свежести: самый свежий выпуск заполняет интервалы первым, пропуски берутся из более ранних; интервалы, истёкшие к `asof.t`, не входят; каждый интервал несёт заметку и провенанс своего выпуска, `data_version` перечисляет использованные выпуски. Причина: снимок kp_forecast около полуночи UTC не содержит строк текущих суток, а текстовый 3-day forecast выходит позже; без слияния ближайшие часы в режиме current оставались без Kp (`Kp: недоступен`). Тест `tests/store/test_views_live.py::test_kp_forecast_fills_a_day_missing_in_the_latest_snapshot_from_the_older_issue`.
- `views_kp.proton_event_probability(asof, day) -> (percent, Provenance) | None`: последний по доступности выпуск daypre (строка `Proton`) или 3-day forecast (`S1 or greater`), покрывающий день.
- Тест: `uv run pytest tests/store/test_views_kp.py -q`; значения в тестах прочитаны из фикстур 8–10 мая 2024 глазами.

## События SEP и прогнозы прихода CME по DONKI (P3-3, D44)
- `views_donki.sep_state_as_known(asof, start, end) -> list[SepStateKnown]`: по сообщениям DONKI с `messageIssueTime <= asof.t` (записи через `AsOf.aggregates`, как GST) состояние событий ≥10 MeV > 10 pfu (`p10_event`) и ≥100 MeV > 1 pfu (`p100_event`) на каждый момент `[start, end)`: отрезки `SepStateKnown(start, end, p10_event, p100_event, provenance, data_version="donki notifications")`, где хотя бы одно событие известно; `p10_event_since`/`p100_event_since` это свойства. Событие `SepEventKnown(energy_mev, threshold_pfu, since, issued_at, confirmed_at, message_id)` это последнее пересечение с началом не позже момента без известного (к `asof.t`) окончания после него; `issued_at` самое раннее сообщение о начале, `confirmed_at` самое позднее сообщение о том же начале с выпуском не позже `asof.t` (горизонт «не дольше N ч после последнего подтверждения» применяет линия, не вид). Пересечения и окончания сливаются по (энергия, время) между записями. Пустой список: сообщений о пересечениях к `asof.t` нет.
- Провенанс DONKI (D81): `SepEventKnown.provenance` это сообщения события, каждое со своей записью файла: самое раннее о начале и последнее подтверждение к `asof.t`, если это другое сообщение; `SepStateKnown.provenance` это сообщения событий отрезка (без повторов). Сообщения других событий и окончаний в провенанс отрезка не входят.
- `views_donki.cme_kp_forecast(asof, start, end) -> KpSeries | None`: 3-часовые интервалы с началом в `[start − 3h, end]`, пересекающие `[arrival − uncertainty, arrival + uncertainty]` хотя бы одного прогноза прихода CME с выпуском не позже `asof.t` и с диапазоном Kp; значение это наибольший `kp_max` действующих прогнозов (при равенстве позднейший выпуск), `kind = external_forecast`, `data_version = "donki notifications"`, `note` «прогноз прихода CME, DONKI/WSA-ENLIL, выпуск …, приход … ± N ч, Kp A–B». Без прогнозов `None`.
- Тест: `uv run pytest tests/store/test_views_donki.py -q`; значения из фикстуры 9–12 мая 2024 глазами: при T = 10 мая 16:00 известно ≥10 MeV с 13:35 (выпуск 13:46, подтверждение 14:12), ≥100 MeV нет; при T = 11 мая 03:00 отрезок 13:35–01:10 с ≥10 MeV и отрезок с 02:10 с обоими событиями (≥10 MeV выпуск 02:46, ≥100 MeV выпуск 02:30, подтверждение 02:46); при T = 10 мая 12:00 пусто; `cme_kp_forecast` при T = 10 мая 00:00 даёт 9.0 на интервалах 06:00–21:00 10 мая (приход 13:03 ± 7 ч, Kp 8–9, выпуск 9 мая 21:24) и 8.0 на 21:00 и 00:00 (приход 23:46 ± 7 ч, Kp 6–8).

## Живые продукты SWPC в текущем режиме (P2-9)
- Выпуски `3day_forecast` читаются из `swpc_archive` и `swpc_live` вместе (тот же парсер, порядок по доступности) в `kp_as_known`, `kp_forecast` и `proton_event_probability`.
- `kp_forecast`: кандидаты дополнены `swpc_live/3day_forecast` и `swpc_live/kp_forecast` (JSON `noaa-planetary-k-index-forecast.json`, `parsers.swpc_json.parse_kp_forecast`); последний по доступности выбирается по `availability_key`. Из снимка JSON берутся строки `estimated` и `predicted` на интервалы, не прошедшие к моменту снимка (`fetched_at`), `data_version = "snapshot YYYY-MM-DD HH:MM"`, `note` со статусом строки. Статус `estimated` в продукте стоит и у ещё не начавшихся интервалов текущих суток, а его значение за текущий интервал совпадает с ячейкой 3-day forecast (фикстура 18 сентября 2026: 15:00 estimated 2.00 при максимуме оценочного Kp по минутам 0.67), поэтому `estimated` это внешний прогноз, не наблюдение.
- `kp_as_known`: приоритет источников после прошедших ячеек 3-day и DONKI: строки `observed` снимка `swpc_live/kp_forecast` (поздний снимок перекрывает ранний, `note` «наблюдённый Kp SWPC из продукта kp_forecast (observed)», version «swpc live observed»), затем максимум `estimated_kp` по минутам `swpc_live/kp_1m` за 3-часовой интервал (`parsers.swpc_json.parse_kp_1m`, поздний снимок перекрывает ранний по минуте, только минуты `<= t`, `note` «оценочный Kp SWPC, максимум за интервал», version «estimated»; текущий интервал получает максимум по уже прошедшим минутам), затем «максимум за 24 ч». `data_version` ряда это перечисление версий использованных ячеек через запятую (только датированные продукты дают прежнее `swpc dated products`).
- Живые записи читаются от поздней к ранней и только те, что получены не раньше `start - 3h`; чтение останавливается на записи, чей первый элемент не позже `start - 3h`.
- Тест: `uv run pytest tests/store/test_views_live.py -q` на фикстурах `tests/fixtures/swpc_live/` (снимок 18 сентября 2026 ~17:19 UTC, в тестах `SNAPSHOT` 17:20): 208 отсчётов протонов за 18 сентября без `NaN`, последний 17:15 с p10 0.2169 и p100 0.1941 pfu; прогноз Kp из JSON 2.0/2.67/3.0 (estimated) и 1.67/2.0/1.67 (predicted 19 сентября); Kp как знали: 17 сентября 21:00 2.33 (observed), 18 сентября 00–09 из ячеек 3-day, 12:00 0.67 (observed), 15:00 0.67 (максимум по минутам).

## Докачка архива по запросу (D59)
- `backfill.py`: `covered_days(store)` сутки с суточным файлом `goes_sgps` по имени файла в url (`mirror_import.goes_file_day`), а без суток в имени дата доступности минус один день; `needed_days(span, cutoff, today)` от `LEAD_DAYS` = 3 суток до начала поиска, а при отсечении от `REPLAY_LEAD_DAYS` = 10 суток до него (глубина `replay.baseline.PERSISTENCE_LOOKBACK`: файл GOES доступен через 6–7 суток, D80) до конца поиска, без суток моложе `PUBLICATION_LAG_DAYS` = 2; `missing_days`; `missing_forecast_years(store, span)` годы периода с прогнозом NASA MEO в реестре, но без записи `meteor_docs/meo_flux_<год>` (D67); `backfill(store, mirror_root, span, cutoff, now, fetch, report) -> BackfillReport | None` докачивает и непокрытые сутки, и недостающие прогнозы MEO, даже если поток протонов за эти сутки уже есть.
- `None` означает, что сеть не нужна. Отказ сети не даёт исключений: ошибки в `BackfillReport.failed`, недостающие сутки в `still_missing`, строки для ограничений результата в `notes()`.
- Импорт идёт через `import_mirror`: классификация и время доступности записей те же, что у ручного зеркала, отсечение `AsOf` работает одинаково.
- `day_ranges`, `ranges_text` используются и текстом «период вне покрытия архива» в `api/service.py`.
- Тест: `uv run pytest tests/store/test_backfill.py -q` на подменённом архиве.
